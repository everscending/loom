Architecture · unattended build loop

loom

A skill that turns a product spec into a build that runs while nobody is watching. This page is the wiring diagram: what fires, what spends, what writes, and where every loop closes.

Vocabulary

Five words, before any wiring

Everything below is built out of these. Two of them are processes, two are records, one is a file on disk.

the build agent

The launchd job. One per repo, label com.loom.<repo>, firing tick.sh tick --auto every 60 seconds. Also called the heartbeat, because that is its whole job: prove something is still alive, and restart the loop if it isn't.

a wave

One headless Claude session running /loom tick. It reads the board, spawns work, writes back, exits. Stateless by construction — nothing carries from one wave to the next except what got written down.

a lane

One headless Claude session doing one piece of work in its own git worktree. Four kinds, told apart by the lane's name alone: impl-, gate-, merge-, probe-.

the tracker

GitLab, reached through glab — its command-line tool. Epics or milestones, a Build N issue, tickets whose labels are their state, merge requests, and review comments. The only mutable build state that exists.

the run directory

~/.loom/<repo>/ — locks, process ids, the event log, lane logs, the stop switch. Plumbing for the machine, deliberately not build state: losing it costs you the loop, never a decision.

the worktree

A sibling directory, ../<repo>-wt-<n>, cut fresh from origin/<base> per ticket. A lane starts inside one and never has to cd anywhere.

The whole machine

What fires, what spends, what writes

Read it left to right: three things can trigger a tick, one script decides whether that tick costs money, and everything expensive happens to the right of that decision.

The name you asked for

The launchd job is the build agent — one per repo, label com.loom.<repo-basename>-<path-hash>, plist in ~/Library/LaunchAgents. In the code it's also called the heartbeat, and the state it can be in is armed or not. /loom start arms it and verifies launchd actually accepted it; /loom stop boots it out; a finished build tears it down on its own, detached, three seconds after the completion report lands.

There used to be two jobs — a scheduler and a separate 60-second watcher. Merging them is why step 1 above sits outside the lock.

Loop 1 · the heartbeat

Why a 60-second timer doesn't cost 60 seconds of model

Watching is free and happens always. Spending is paced by a separate clock, and a finishing lane is allowed to skip that clock.

Loop 2 · one ticket

Every state change is a label, and one verb writes it

The inner loop. A ticket's labels are its state — there is no other record — and the lane never touches glab directly to change one.

Loop 3 · one epic

The outer loop nobody has to be awake for

An epic isn't done when its tickets close. It's done when something has driven it the way a user would — and a failed probe feeds straight back into the ticket loop.

Config resolves in four layers

Repo → derived → global → built-in. tick.sh resolve-config prints the merged document with each value's source, so the effective setting is one command away rather than something to reason about. The derived layer is the interesting one: the base branch, the gate commands, and the whole permission surface are all read off the repo, and the permission allowlist is generated from the same commands the gates will run — so it cannot drift from them.

Phases

Everything above is phase six

The first five phases are a human sitting with the machine. The sixth is the one that runs overnight — and it is the only phase with a loop in it.

verbphasewhat it produces
plan <spec>1–2architecture and UX grilled to closure: decision records, an architecture doc, a UX spec
epics3the epic breakdown, created in the tracker, each carrying its own acceptance criteria
tickets4tickets with contracts, gate tiers, spec IDs and blocking edges
build5a Build N issue selecting epics — and it deliberately never starts anything
start5→6the trigger: arms the build agent, clears the stop switch
tick · watch · unblock · stop6one wave · a narrated view · a human decision · the switch off
retroafter 6where the time and money went, written up as proposals

Verb boundaries are hard stops: a verb ends at its own output and hands back to the human. It never auto-advances to the next verb, and never implements by hand — a rule paid for by a run that chained plan → epics → hand-coding under a deadline.

Two more things wired into phase six

notifications

Build complete, halted, stalled, ticket blocked, lane stale, workspace untrusted, no heartbeat. Pushed to an access-protected topic on ntfy — a phone-push service — via curl, or — with no topic set — a local macOS banner. The event is recorded in the ticker first, before any decision about pushing, so a misconfigured push can't also silence the record.

the viewer

Inside herdr — the terminal multiplexer this runs in — watch-panes.sh raises a pane per live lane plus a ticker strip. Two switches, both honored mid-run — q in the ticker pane, and the whole viewer off — and only start and watch may clear them, so an automatic tick can never undo a human's close.
