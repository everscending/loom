## Independent review round (2026-08-01)

After P1–P22 landed with 147 tests passing, two independent reviewers — separate
sessions, no knowledge of the reasoning behind the code — read `tick.sh`, `tick-test.sh` and
`bootstrap.sh`. They found **fourteen real defects** in the scripts, and twelve more in `SKILL.md`. A third pass, verifying the fixes, found
**five more that the fixes themselves introduced**. Suite: 147 → 175.

**What that says about the tests, which is the useful part.** A green suite was not evidence.
Three of the worst findings were *caused* by the tests:

- `tick-test.sh` had an assertion calling `ok` in **both** branches — it could not fail, and its
  planted-violation partner passed vacuously on an empty file. The whole ntfy subsection reported
  safety it never checked.
- The duplicate-dispatch test planted a single verdict note, so verdict *ordering* was never
  exercised — hiding that `gate_of` returned the OLDEST verdict at a HEAD.
- The graph frontier fixture happened to include one unblocked ticket, hiding that
  `opening_width` read `levels[0]` whatever its depth.

A planted violation only proves what it plants. Each of these had one, and each plant missed the
axis that was broken.

**The pattern in the fixes.** Four of the five *newly introduced* defects were ordering or
fallback errors, not logic errors: destructive work (log rotation, clearing `<id>.rc`) placed
above a guard that can still refuse; a sort whose tiebreak silently restored the original bug when
a field was absent; a validation hardcoded to four tier names that broke repos declaring their
own. Fixing a bug moves the failure to its edges.

**Then SKILL.md itself, which nothing had reviewed** — the one file loaded into every wave. Twelve
more findings, and the two worst were places the *prose* and the *machinery* had drifted apart:

- `probe-<epic>` with a real epic title ("Ledger core") produced the lane id `probe-Ledger core`.
  `lane-status` is a space-delimited format, so the snapshot parsed that lane as
  `{id: "probe-Ledger", pid: "core", state: "<pid>"}` — and a state that is never `dead` counts
  as a live lane for the rest of the build. The id grammar is now charset-checked at spawn.
- `unblock` removes the `blocked` label but never clears the **assignee**, while the ready set
  requires *unclaimed*. An unblocked ticket was therefore invisible to fill-lanes, and a build
  with nothing else outstanding would report `build_complete` and tear down its own agent with
  that ticket still open.

It also caught `crash_cap` doing two unrelated jobs (per-ticket implementer crashes *and*
consecutive wave failures, the second added by P15) — so lowering it to calm a flapping ticket
also made the whole build halt sooner. The wave-failure threshold is a constant now. And the
phase-4 width check introduced by P8 ran `snapshot | graph` **before** the `Build N` issue
exists, so it always answered "no tickets in this build"; the measurement moved to phase 5, where
the build is real, and phase 4 keeps the design rule.

**Two runtime lessons worth keeping.** `_rotate_log` skips empty files — correct, nothing to
preserve — which left the old file in place with its old mtime, so a lane respawned under an id
whose previous run wrote nothing read as `stale` immediately and would be killed. Truncating in
place is what makes "a reused id cannot inherit an old mtime" true. And `bootstrap.sh` took
`REPO_ROOT` from `$PWD` with the git check *after* the write: run from `$HOME` it would create
`~/.claude/settings.json`, the human's own configuration.

## Independent review round (2026-08-06)

Eight independent reviewers — one per file, none told what the others found or why the code looks
as it does — read `tick.sh`, `snapshot.jq`, `lane.sh`, `bootstrap.sh`, `watch-panes.sh`,
`tick-test.sh`, `SKILL.md` and `references/*.md` against a suite that was **green at 430 tests**,
with `snapshot | graph`, `lane-status` and `report` all clean against a live tracker. They found
**78 defects**, and every one of them was confirmed against the real lines before it was reported.
None of it was reachable by running the tests.

**What that says about the tests, again, and worse.** The suite grew from 175 to 430 tests and
its trustworthiness did not grow with it. Twelve tests were found that cannot fail or prove
something other than what they name, and the two most dangerous guard the two most destructive
mechanisms in the program:

- The prune-guard test (`tick-test.sh:394-397`) never invokes `tick.sh` at all. It writes its own
  `case` statement inside a `bash -c` string and asserts on that — it is testing the bash `case`
  builtin. Deleting `tick.sh:124`, the line that stands in front of the only unbounded `rm -rf`
  in the project, leaves it green.
- The event-log invariant test (`tick-test.sh:2902-2906`) greps for readers matching
  `(<|read|cat|jq…)`, so it cannot see a reader written with `tail` or `grep`. Two production
  *decision* readers already exist and it is green over both: `_last_activity_ts` (`tick.sh:285`,
  `tail`) feeds the spend gate, and `_wave_gap_ok` (`tick.sh:731`, `grep`) decides whether a wave
  runs at all. The invariant the test names — constitution rule 1 — is already false in the code.
- The read-only-snapshot test (`tick-test.sh:2019-2023`) denylists `issue update|mr merge|…`,
  but every tracker mutation in this codebase is written as `glab api --method PUT|POST`. It
  would pass over a snapshot that relabels tickets.
- The `ok`-in-both-branches pattern, killed in the ntfy block on 2026-08-01, survived at
  `tick-test.sh:2361-2363`. A guaranteed +1 to the pass count.

A planted violation still only proves what it plants — and a planted violation with no check that
the mutated copy *ran* proves nothing at all. Three watch-panes tests pass against a stand-in that
is `exit 127`.

**One bug class ran through four files at once: `stale` means alive.** `lane-status` reports
`running | stale | dead`, where `stale` is "pid alive, no model turn for `heartbeat_stale_minutes`"
— the wedge state a human must triage. Four independent consumers filter on `running` alone and
therefore treat a live lane as gone:

- `cmd_sweep` (`tick.sh:164`) collects live cwds from `running` lanes only, so a stale lane's
  worktree is eligible for `git worktree remove --force` + `rm -rf` — under a live process, with
  its uncommitted work in it. The comment two lines below names this exact outcome as what the
  guard exists to prevent.
- `_quiet_check` (`tick.sh:301`) counts only `running` as activity, so a build whose last live
  lane is stale classifies `halted` (or `complete`) and pushes that to the human.
- `watch-panes.sh:408` closes a stale probe's pane and destroys its scrollback, and stamps a
  stale `impl-N` pane "idle" — which then makes it a reuse candidate for another ticket.

**And a second class: guards that fail open.** Every guard read in `lane.sh` is
`… 2>/dev/null … || true`, so a transient API failure makes the guard *pass*. One GitLab 502
during a build and `close` closes over an unmerged MR, or a lane walks straight through a human's
`blocked` hold — reporting success both times. The same shape sits in `cmd_sweep`'s merge check
(`tick.sh:190`), where a `git log` that exits 128 on an unresolvable revision range is
indistinguishable from "no commits ahead", and arms the delete path.

**Prose and machinery drifted apart in a new place: the wave prompt.** `tick.sh:885-891` composes
the context injected into every wave, prefaced "trust it over rediscovery" — so where it
contradicts `SKILL.md`, it wins, from inside. It currently tells every wave to spawn lanes with a
flat `--model <lane_model>` (defeating P31's per-ticket escalation, so a rework round runs on the
tier that just failed), lists the `lane.sh` verbs without `merge`, `merge-failed`, `fix-ticket`,
`reconcile` or `probe-result`, and instructs merge lanes to finish with `lane.sh close` — the
build-1 merge-1 failure that `cmd_merge` was written to end, and which `cmd_close` now hard-refuses.

**Runtime lessons worth keeping.** Tracker reads that decide acceptance and quiescence
(`tick.sh:246`, `:247`, `:306`, `:1889`) are capped at one page with no `--paginate`: past 100
closed members, an epic whose tickets all closed early contributes no milestone title, so the
build reports `complete` and tears itself down with that epic never probed — the build-2 failure
the whole gate was written for, reachable again by size alone. Both locks stamp the owner pid
*after* the `mkdir` that claims them, so a second tick landing in that window reads an unstamped
lock as a dead-owner lock and breaks it: two concurrent waves, or two merge lanes, from a race the
comment says is impossible. And `snapshot.jq` matches epics to milestones with bare `startswith`
in both directions while `lane.sh` matches on an exact-or-dash-boundary rule — so with epics `E1`
and `E11 Reporting` in one build, a passing `E1` probe closes `E11`'s milestone, reads `E11`'s
acceptance criteria into `E1`'s brief, and leaves `E1` permanently unaccepted.

All 88 defects are recorded with stable `D-<FILE>-<nn>` keys in
[OPEN_DEFECTS.md](OPEN_DEFECTS.md), each with its location, failure scenario and test gap. The
subset that needs a change rather than a fix is P45–P50 in `PROPOSALS.md`.

## Why this order

P1–P3 are first not because they save the most minutes on a good run, but because each is a
way the build stops completely, and a halted build has infinite latency. P8 is the largest
ceiling-raiser on the list — it is ranked eighth only because it is a practice change rather
than a bug fix, and it pays off solely once the loop reliably keeps running.

## P1 · Don't throw away the "a lane just finished" signal

When a lane finishes it tries to kick off the next scheduling wave. If a wave happens to be
running at that moment, the kick is discarded and nothing remembers it happened.

**Evidence.** `cmd_tick` (tick.sh:78) exits 0 with "wave already running — skipping" and drops
the event; `tick-test.sh` case 1a asserts this as correct behaviour. `self-trigger.log` holds
ten such lines. The last line in that file is one of them: `gate-14` exited at 23:36:03 while
W13 held the lock, the signal was dropped, no heartbeat was armed, **and the loop never ran
again** — leaving #14 sitting in `merge-queue`, unmerged. Two further signals vanished with no
log line at all (`lane-15` at 20:56:07, `lane-17` at 21:39:03, the latter producing a 25m02s
stall with no lock contention to explain it).

**Fix.** On skip, leave a note — `touch "$LOOM_HOME/tick.pending"`. The lock holder checks the
flag on exit and re-execs one tick if set. Coalescing, so a burst of finishing lanes costs one
extra wave rather than one per lane.

**Implemented 2026-08-01, with P2.** They are one change: P2 makes every lane fire a tick, P1
makes sure a fire that lands mid-wave is not discarded. Shipping P2 alone would have produced
*more* dropped signals, and P1 alone would only have covered the lanes someone remembered to
flag.

The whole proposal is ordering. `cmd_tick`'s lock was released by an `EXIT` trap, so the replay
had to go **inside** that trap, after the `rm -rf`: a follow-up tick fired while this process
still held the lock would find the lock taken and skip — reproducing the exact bug it exists to
fix. `_tick_exit` therefore replaces `lock_acquire`'s plain trap for the tick path only, which
also picks up the `wave exited nonzero` path for free.

The note is a single flag, not a queue, and that is the design: three kicks landing during one
wave must produce one extra wave, not three. There is one small race — a tick skipped in the
instant after the holder's check — and it self-heals, because the *next* wave's exit sees the
note and replays it. The cost is one spurious wave, never a lost signal.

The test that states the proposal counts waves: the wave command appends a line, so the file
length is the number of waves that ran. Three mid-wave kicks → exactly 2. Its planted violation
points the skipped ticks' note at a path the holder never reads — the old drop-on-the-floor
path, reached through the existing `LOOM_PENDING_FILE` seam rather than by editing the script —
and shows the loop dying after a single wave, which is how build 2 actually ended.

**Two things this shook out of the test suite.** With self-trigger on by default, every lane in
`tick-test.sh` now fires a tick when it exits, so the file needs a harmless default
`LOOM_WAVE_CMD` or those ticks launch real `claude` sessions. It also needs bootstrap off by
default (`LOOM_SKIP_BOOTSTRAP`), now that many more ticks pay for it — section 9, which tests
bootstrap itself, switches it back on through `BOOTENV`. Both are the kind of blast radius a
default change has and an opt-in flag does not.

## P3 · Actually arm the safety-net timer, and check that it worked

A slow background timer exists to restart a stalled loop. It was never running.

**Evidence.** Eight of thirteen waves report `agent-status: not loaded` and spend a paragraph
advising the operator to run `/loom start` (W1, W2, W4, W5, W9, W10, W12, W13). The
entire run therefore depended on the self-trigger chain — precisely the mechanism dropping
signals in P1.

**Re-opened 2026-08-02 (build-1).** The deferral reason — "the skill is driven by `tick` alone" —
is exactly how build-1 paid: the loop was kicked with manual `tick` on Friday night and left
unattended with nothing armed. When wave-074603 fizzled at 07:46 (Bash denied wholesale, misread
as "never bootstrapped", exited without harvesting), **nothing fired again for 2h08m** until the
human ran `start` at 09:54 — after which #1 merged within 30 minutes. The stderr warning shipped
since crucible fired on every tick, fifteen times, into a log nobody was reading overnight. Two
additions to the fix:

- **The warning must reach the human, not the log.** Route the un-armed warning through
  `tick.sh notify`, once per state change like the quiescence watcher — an un-armed build should
  produce one push, not fifteen stderr lines.
- **The armed-check is wrong from detached contexts.** After the agent was armed at 09:54
  (launchd demonstrably fired wave-095403; `uninstall` at 12:28 unloaded it), every later
  self-triggered tick *still* warned "not installed": `launchctl print gui/$(id -u)/$LOOM_LABEL`
  fails from a nohup'd lane context. Probe the installed plist file first, with `launchctl list`
  as fallback.

**Fix.** `start` verifies the agent actually loaded and fails loudly otherwise. A wave that
detects `not loaded` installs it rather than advising about it thirteen times.

**What would falsify it.** An un-armed build that does not push a notification within one tick,
or an armed build that still logs false "not installed" warnings.

**Implemented 2026-08-07.** Four pieces, all in `tick.sh`:

- `_agent_armed` reads the **installed plist file** first and falls back to `launchctl list`
  (domain-free) and then `launchctl print`. That is what makes the check honest from a detached
  lane. The plist file only ever exists when launchd accepted it: `_arm_agent` moves a rejected
  one to `$LOOM_HOME/<label>.plist.rejected`, and `install --dry-run` writes its preview to
  `$LOOM_HOME` instead of `LaunchAgents`, so neither can leave a build reading itself as
  protected when it is not.
- `_arm_agent` is the shared arming path — write plist, bootout, bootstrap, retire the old
  watcher, **verify the load**. `start` fails loudly (naming the rejected plist and the
  `launchctl bootstrap` line to try by hand) when it returns non-zero.
- `_ensure_armed` runs on every tick before any gate — the firing that gets skipped is exactly
  the firing after which nothing else may fire — and *arms* rather than advises. Skipped while
  the loop switch is off, so a tick can never re-arm a deliberately stopped build; only `start`
  reverses a `stop`.
- When launchd refuses, the `build_unarmed` push goes out **once per state change** against
  `$LOOM_HOME/agent.unarmed`, the same sentinel shape the quiescence watcher uses. Added to the
  default push list in `bootstrap.sh` and documented in `references/loom-config.md`.

The stderr warning it replaces is gone, and `agent-status` grew a third answer — `armed`, the
plist installed but launchd unreadable from here — instead of reporting a running agent as "not
loaded". 14 tests in `tick-test.sh` §4j, including the two planted violations that matter: a
refused load must leave no plist behind, and the detached-context check must pass on the plist
rather than on silence.

## P4 · Check that every spawned session's commands are allowed to run

The `api` gate tier cannot run unattended as configured, and the mismatch is mechanical. The
same mismatch silently disabled the E4 acceptance probe (see P16).

**Evidence.** `.loom.yml` specifies `CRUCIBLE_LIVE=1 uv run pytest -q
tests/test_target_live.py`; `.claude/settings.json` allows `Bash(uv *)`, which does not match a
command beginning with an environment-variable assignment. The cost: `lane-13.log:42-54` shows
a gate session that completed its full review and 230 tests, then issued **no verdict at all**
— *"Both writes would misreport, so I stopped. I need permission to run command 3."* The whole
review had to be redone. Same class of failure blocked `rm` (`lane-15.log:27` left two scratch
files behind, one of which "makes a live unstubbed HTTP call to the seeded target") and long
`glab issue note` bodies (`lane-17.log:51` had to split a verdict across two comments).

The probe case is plausibly the same defect with a wider blast radius. `cmd_spawn_lane` runs
`nohup "$@"` with no `cd` (tick.sh:98-134), inheriting the wave's cwd — `$REPO_ROOT`, the base
clone — so every lane must `cd` into its own worktree, and `Bash(cd *)` is not in the allowlist.
That fits *"denied every command touching the `crucible-probe-e4` worktree"* precisely, though
workspace trust is a competing explanation (see P16). The E11 probe succeeded under the
identical allowlist because it ran inline in the wave session, already in the repo root, and
needed only `uv run crucible serve`. A live probe also needs `curl` and `sleep`; neither is
allowed.

**Fix.** Bootstrap validates that every command any spawned session must run — gate tiers *and*
the probe's live-stack commands — matches the committed allowlist, and fails the bootstrap if
any does not. Lanes should also be spawned with their worktree as cwd rather than `cd`-ing
there, which removes the need for a `cd` rule at all.

**Implementation notes (2026-08-01).** Three parts, and one deliberate non-fix.

*Allowlist.* Validation became generation under P22 — `_derive_allow` emits each gate tier's
literal command with its environment prefix, so `CRUCIBLE_LIVE=1 uv run pytest` produces
`Bash(CRUCIBLE_LIVE=1 uv *)`, plus `curl` and `sleep` for the probe's live stack. A generated
allowlist cannot mismatch what it was generated from, so there is nothing left to validate.

*Lane cwd.* `spawn-lane` takes `--cwd <dir>` (order-tolerant like `--on-done-tick`, composes
with it), runs the lane there, and dies loudly on a path that does not exist rather than
producing a lane that fails its first command and reads as an ordinary crash. The log redirect
is attached to the subshell so it resolves before the `cd`. `Bash(cd *)` is **removed** from the
generated allowlist and a test now asserts its absence — if it reappears, the spawn fix was
bypassed. SKILL.md's three spawn call sites carry `--cwd <worktree>`.

*Long notes.* The `glab issue note` block is command *length*, not a missing rule, so no allow
entry can fix it. Lanes now write the body to a file in `$LOOM_SCRATCH` (a per-session directory
`tick.sh` creates and exports, because no spawned session may run `mkdir`; it began as a
per-repo `$ORCH_NOTES` and was folded into P17's scratch when that landed) and post it with
`glab api ".../notes" --field body=@<file>` — verified against glab 1.107.0, which reads the
value from the file and errors before any network call if it is missing.

*Not fixed: `rm`.* P4's evidence also had `lane-15.log:27` leaving two scratch files behind, one
making a live unstubbed HTTP call to the seeded target. That is the **guardrail hook**, not the
allowlist — `lane-15.log` says so outright — so no allow rule reaches it. Loosening a
deliberately-installed safety hook is the wrong fix; P17's per-wave scratch paths should give
lanes a scratch location nobody has to delete. Left to P17.

## P5 · Get slow work out of the scheduler and into lanes

Long-running work executes inside the wave session, holding the global tick lock.

**Evidence.** W8 (`wave-20260721-221123.log`, 22:11:23–22:28:32) did nothing but run the E11
acceptance probe — a real `crucible serve` against the live target — for **17m09s** with the
lock held. `lane-18` exited at 22:20:20, mid-probe, and lost its signal
(`self-trigger.log:15`); the next wave came 36 minutes later. The merge queue has the same
shape: fetch, rebase, re-gate, merge, teardown, serialized against harvest/gate/fill, when only
the merge itself needs single-writer semantics.

**Fix.** Probes and merges become their own lanes, never inline wave work. Split the merge lock
from the tick lock. Precedent already exists in the run: `lane-gate-13-merge.log` is a merge
that ran as a lane.

**Implemented 2026-08-01.** Probes became lanes with P16; merges now do too. `spawn-lane
--merge-lock` reserves a second lock (`merge.lock.d`) *before* spawning — a refusal leaves no
lane and no pid file, like every other spawn guard — then stamps the lock with the lane's pid
once it exists, because tick.sh is about to exit and a lock owned by a dead pid is a lock anyone
may break. The lane releases it on exit, ahead of firing the next wave, so the merge that just
finished cannot block the one it unblocked. A killed lane leaves a directory whose owner is
dead, and the existing stale-lock rule breaks it: the worst case is one skipped merge, never two
merges at once. `summary.merge_in_flight` tells the wave a merge is running without it having to
touch the lock.

The test that states the proposal is the pair: a second merge lane is refused while one holds
the lock, *and* a wave still ticks normally in the same moment. Its planted violation points the
tick lock at the merge lock's directory and shows the wave stalling — the old behaviour, where
harvest, gate and fill all queued behind a rebase-and-merge.

What is deliberately not here: the wave still decides *when* to spawn a merge lane. The lock
makes concurrent merges impossible; it does not schedule them.

## P6 · Let a ticket go implement → gate → merge without a scheduler hop

Each ticket bounces off the scheduler two or three times, and neither hop makes a decision: a
ticket in `review` always gets gated, and a passing gate always goes to the merge queue.

**Evidence.** The path is implementer exits → wave → gate exits → wave → merge inside a wave.
`git log` shows #13's implementation commits at 20:22 and its merge at 23:02.

**Fix.** The implementer spawns its own gate; the gate's pass path enqueues to a merge lane.
The wave then only does what needs global knowledge — filling lanes and triaging crashes.

**Implemented 2026-08-01, with P9** — both restructure the same phase-6 step list, and doing them
separately would have meant editing it twice.

**The governing rule is "fast path, never the only path."** The wave composes each session's
prompt already, so it now hands the session the exact `spawn-lane` line for the next stage and
the session runs it as its last act. Every handoff is *allowed* to fail — merge lock held,
session died, cap reached — and nothing depends on one, because the numbered steps still do the
same work on the next wave. That is what keeps a latency optimisation from becoming a new way for
the build to stop, which is the failure class P1 through P3 are all about.

**One guard was genuinely required.** A chaining implementer also fires a completion tick, so the
very next wave sees its ticket in `review` with a verifier already on it — and would spawn a
second gate under the same id, overwriting the running pid file and rotating that log away. So
`gate.eligible` is now false while a gate lane for that ticket is running. It rides P11, which is
why the two wanted doing in this order. Its planted violation is the *release* case: once the
lane is cleared the ticket must become gateable again, or a rejected ticket could never be
re-reviewed.

**Deliberately not done: a lane-count cap inside `spawn-lane`.** It looks necessary — a
self-spawned lane consults no snapshot, so nothing checks `max_aux_lanes`. It is not, because the
chain is strictly one-for-one: each lane spawns at most one successor *as it dies*, so an
implementer slot frees exactly as an aux slot fills. Chained gates are bounded by the
`max_lanes` implementers that produced them, and merges are serialised by the merge lock
regardless. Adding the cap would have put a timing-dependent refusal in front of roughly forty
existing lane spawns in the test suite to solve a problem the shape of the chain already
prevents. If a future change breaks that one-for-one property, this is the first thing to
revisit.

**What P6 no longer buys.** Its evidence was 4–9 minute waves, but P7's snapshot removed most of
that. A hop now costs one wave session rather than eight minutes of tracker round-trips, so this
is a smaller win than the original ranking implies — worth having, not worth contorting for.

## P7 · Stop making the scheduler rediscover everything from scratch

Each wave asks the tracker thirty-odd questions one at a time before doing anything.

**Evidence.** Lag from wave start to first lane spawn: W9 started 22:56:25 and spawned
`lane-14` at **23:05:11** — 8m46s before implementation began, with the probe spawn 10m32s in.
W11: 4m49s. W12: 4m59s. Since one `glab` call costs 0.4 s, essentially all of that is model
round-trips.

**Fix.** Add `tick.sh snapshot` — one deterministic command emitting a single JSON document
(open `build-N` issues, labels, assignees, blocked-by edges, `lane-status`, lessons tail), with
the queries run concurrently in shell, injected into the wave prompt. Roughly thirty
round-trips become one. This does not violate the no-shadow-state rule: the snapshot is
derived, read-only, and discarded each wave.

## P8 · Widen the ticket graph so there's parallelism to exploit

For the first hour the build had four lanes available and zero or one startable ticket.

**Evidence.** W1: *"Frontier is 1 wide until #12 merges; it opens to 3 the moment it does."*
W2: *"2 of 4 lanes are free, but neither `ready-for-agent` ticket is actually unblocked."*
W5: *"The frontier is genuinely 0 wide until one of these two gates passes and merges."* Peak
concurrency across the whole run was 2.

The cause is upstream in phase 4: `/to-tickets` asks whether the blocking edges are *correct*
and never whether the graph is *wide*.

**Scope check (2026-08-01).** This is the one proposal whose write-up names a sibling skill, so
to be explicit: the fix needs **no change to `/to-tickets`**. Phase 4 already routes to it *plus*
a list of additions this skill owns in `references/ticket-template.md`, and the pinned-interfaces
rule the fix leans on is itself one of those additions. Frontier width becomes another item on
that list; the critical-path report belongs to this skill's own `build` verb. Naming the cause as
upstream was diagnosis, not a plan to edit upstream.

**Fix.** Make frontier width a first-class phase-4 output. Exploit the **Pinned interfaces**
rule the skill already has — if a signature is pinned verbatim in every affected ticket, the
dependent needs the interface, not the merged blocker, so a heavy blocker can split into a tiny
"interface + stub" ticket that merges fast and an implementation that follows. Have `build`
print the critical path and the maximum achievable parallelism next to `max_lanes`, so a
chain-shaped build is visible before it starts rather than discovered by wave 1.

**Implemented 2026-08-01, entirely inside this skill** (see the scope check above).

*Measured, not asserted.* `tick.sh graph` reads a snapshot on stdin — so it costs no extra
tracker calls — and reports how wide the build **opens**, how wide it ever **gets**, its critical
path in merge cycles, and the level structure. Those first two are different questions, and build
2 lost its hour to the first: "frontier is 1 wide until #12 merges; it opens to 3 the moment it
does". Both are always reported; the verdict labels `CHAIN-SHAPED` or `NARROW START` accordingly.

*Honest about what the number means.* `widest_level` is a **lower** bound on real concurrency,
not the true maximum: once a depth-0 ticket merges its dependent can run beside another depth-0
ticket. The true maximum antichain needs bipartite matching and would not change a single
decision. The lower bound is still the right alarm, because a build that cannot fill its lanes
*at the start* is chain-bound exactly when that costs most.

*A real bug the fixtures could not have caught.* The first version dropped blocking edges to
issues outside the build, since the graph has no depth for them — and crucible then reported
"opens 7 wide" when three of those seven were waiting on out-of-build issues. False reassurance
is worse than no report at all. Out-of-build blockers now carry no depth of their own but do push
their dependent off depth 0. Every synthetic shape passed; this surfaced only by running it
against the live tracker and noticing the answer disagreed with the snapshot own `unblocked`
flags. Regression test added.

*Crying wolf was the other risk.* A build with fewer tickets than lanes is **small**, not
chain-shaped, and a build that fills its lanes is fine however deep it runs. Neither raises
anything, and both have planted-violation tests — a warning that fires on healthy builds trains
the human to skip the line that matters.

*The prose half* is two additions this skill owns. Phase 4 treats width as an output to check and
reshape rather than an afterthought, and `references/ticket-template.md` documents the
**interface + stub** split as what the Pinned-interfaces rule is *for*: a dependent needs its
blocker signature, not its merged body, so a heavy blocker becomes a tiny stub ticket that merges
in one cycle plus the implementation behind it. `build` reports the shape beside `max_lanes`
before anything spends. The test that states the proposal is the split itself — the same four
tickets go from opening 1 wide to opening 4.

Phase 6 currently orders the steps harvest → gate → merge → fill, putting the slowest step

**Fix.** Swap the order. With P5 in place the merge lane's own completion signal picks up

**Implemented 2026-08-01, with P6.** Phase 6 steps 4 and 5 swapped, and the reason is written

## P10 · Count only implementation lanes against the lane limit

**Evidence.** `cmd_lane_status` globs every `*.pid`, and SKILL.md step 5 says "while lanes <
`max_lanes`" — so two gates plus a probe turns `max_lanes: 4` into one implementer. Lane ids in
the run were ad hoc (`12`, `gate12`, `gate-12-r2`, `impl-14`, `probe-e4`), so the lane type
cannot reliably be derived even if you wanted to.

**Fix.** Structured ids (`impl-<n>`, `gate-<n>-r<k>`, `probe-<epic>`, `merge-<n>`), a type
column in `lane-status`, and only `impl-*` counted against `max_lanes`; gates and probes get
their own cap.

**Implemented 2026-08-01.** The id shape is *enforced*, not documented: `spawn-lane` refuses
anything that is not `impl-<n>`, `gate-<n>[-r<k>]`, `merge-<n>` or `probe-<epic>`, because it is
the only place a lane id is ever created. `12`, `gate12` and `lane_14` — all forms the observed
run actually used — now abort at spawn with a message listing the four shapes. `lane-status`
gains a type column **last**, so existing readers that index state at `$3` are untouched.

The wave reads its budget from the snapshot rather than counting pid files: `summary
.lanes_running_by_type`, `summary.impl_slots_free`, and a new layered `max_aux_lanes` (default
4) for gates, merges and probes. The test that states the proposal: four lanes running — two
gates, a probe, a merge — with *every* implementer slot still free. Under the old counting that
was one implementer left out of four.

Two test-authoring notes worth keeping: the snapshot's call-count test shares a stub log, so any
new snapshot call needs its own; and `max_lanes` is layered config, so a test must compare
`impl_slots_free` against the resolved cap rather than a literal 4 — this machine's global
config says 2. jq also rejects an unparenthesised `-` as an object value, which is why

## P11 · Don't gate something already gated or already merged

**Evidence.** W1 spawned a 12m53s verifier on #12 — code merged **95 seconds earlier**
(`lane-gate-12-r2.log`: *"MR !13 was merged manually into `develop` at 00:56 UTC… the worktree
was deleted mid-review"*), which dutifully produced a FAIL verdict on shipped code. Separately,
#14 was gated twice at the identical commit (`lane-gate-14.log:12`: *"already… `PASS (rejection
attempt 3 of 3)`… posted against this exact HEAD (`e52b7c1`)… likely a duplicate/stale
dispatch"*), the duplicate re-running the full `api` suite including the live network test —
about four minutes — before noticing.

**Fix.** Before spawning a gate, confirm the ticket is still in `review`, its MR is still open,
and no verdict comment exists for this HEAD.

**Implemented 2026-08-01, with P12** — both are "do not spend a review session you did not need
to", and both hang off the gate spawn.

The check is **derived in the snapshot**, not left to the wave: each ticket carries
`gate.eligible`, `gate.reason` and `gate.head`, and `summary.gateable` counts what is genuinely
worth a verifier. A rule the wave has to remember is a rule the wave eventually forgets — the
whole of P7 was moving this class of work out of the model's head.

Two of the three conditions were already answerable from data the snapshot held. The third —
"no verdict for this HEAD" — needed a convention, so verdict comments now end with
`<!-- orch-verdict PASS|FAIL <head-sha> -->`, and the MR's `sha` joined the projection. Short
shas match long ones in either direction, because verdicts get written by both humans and models
and both abbreviate. Cost: one extra API call per ticket in `review`, riding P7's existing
concurrent fan-out, so it is a call but almost no wall clock.

**The planted violation is the interesting one.** It is not "a duplicate slipped through" — it is
a verdict on an *older* commit failing to suppress the gate. Get that wrong and a ticket that was
rejected, fixed and re-pushed would never be re-reviewed, which is a far worse failure than the
duplicate the rule exists to prevent. That test is the reason the sha comparison exists at all
rather than a simpler "has any verdict" check.

**A jq trap worth recording.** `$head | startswith(.sha)` does not do what it reads like: the pipe
rebinds `.` to `$head`, so `.sha` indexes the sha *string* and the whole snapshot dies with
"Cannot index string with string". The element has to be bound first (`. as $v | …`). It failed
loudly, which is the good case — but a snapshot that dies takes the whole wave with it.

## P12 · Run the cheap mechanical checks before spending a review session

The deterministic suite is effectively free but currently sits inside a multi-minute agent
session that has already done its expensive reasoning.

**Evidence.** The merge re-gate lane took 4 seconds wall-clock. At least twenty full-suite runs
are quoted across the logs (198 → 270 tests); roughly half are re-runs against an unchanged
tree — implementer runs it, verifier re-runs the identical gate at the same HEAD, merge runs it
a third time.

**Fix.** Run `scripts/gate.sh <tier>` first, in shell, before spawning any review session — a
red branch then rejects in ~15 s with zero model time. Have the implementer run its own tier
gate before pushing so reviews rarely see a mechanical failure. Keep the post-rebase re-gate;
at four seconds it is free.

**Implemented 2026-08-01, with P11.** `spawn-lane --pregate <tier>` runs the repo's own gate
runner inside the lane, in shell, before the session starts. Inside the *lane*, not the wave:
running it in the wave would put a multi-second command back under the tick lock, which is the
thing P5 exists to prevent.

**Exit code 7 is the contract.** A wave has to tell "this branch is mechanically broken, post a
rejection" apart from "the session crashed, resume it", so lanes now record their exit code to
`<id>.rc`, surfaced as a new last column in `lane-status` and as `rc` in the snapshot. The code is
written *before* the completion tick fires, or the wave this lane wakes would race the file it
needs.

**Two failure modes the tests pin down.** A missing gate runner **skips** the pregate instead of
failing it — rejecting a ticket because the repo has no gate script would be a false verdict, and
a false rejection costs far more than a wasted session. And a rejected lane still runs its
epilogue: skipping the session is the point, but skipping the completion tick would halt the
build, which is P1 and P2 re-entering through a side door. Both have their own test.

The implementer half is a SKILL.md prompt change — it runs its tier gate and fixes what it
reports before pushing. The post-rebase re-gate in the merge lane is deliberately left alone: it
runs *after* the rebase, so `--pregate` (which runs before the lane's command) is the wrong tool
there, and at four seconds it is free anyway.

## P13 · Stop mistaking a busy lane for a dead one

Liveness is judged by log mtime, but headless sessions buffer output until exit — so a healthy
lane working past `heartbeat_stale_minutes: 30` looks silent, is classified as wedged, and is
killed, losing all its work.

**Evidence.** W1 spotted this in-band and worked around it by naming a lane `gate-12-r2`,
noting *"That's a convention, not a fix."* The convention was then applied inconsistently:
`lane-13.log`, `lane-15.log`, `lane-17.log` and `lane-gate-14.log` each stack two to four
sessions in one file, which is why several session boundaries in this run are unrecoverable.

**Fix.** `--output-format stream-json --verbose` on spawned sessions (or an explicit heartbeat
touch), plus `:> "$log"` in `cmd_spawn_lane` so a reused id cannot inherit an old mtime.

**Implemented 2026-08-01.** The "or an explicit heartbeat touch" alternative is wrong and should
not be revisited: a timer that touches a file proves the *wrapper* is alive, which is never in
doubt — the pid check already covers it. Streaming is the only signal that distinguishes working
from wedged, because it comes from the session doing work.

*Two files, one lane.* The stream goes to `lane-<id>.jsonl` and `lane-status` reads **that** for
liveness; `render-log <id>` turns it back into prose plus the commands the lane ran, appended to
`lane-<id>.log` as the lane exits. Logs stay plain text, which matters because SKILL.md has waves
tailing them for verdicts and crash triage — a JSONL-only log would have made every reader need
`jq`. The render runs *before* the completion tick fires, so the wave this lane wakes cannot race
its own transcript. stderr still goes straight to the `.log`, so a session that dies before
emitting anything (P15's three 15-byte `Execution error` logs) still leaves its error where
someone will look.

*Injected, not requested.* `spawn-lane` adds the flags itself when the command's basename is
`claude` — the P2 lesson applied again, since a flag whose omission silently breaks liveness must
not be optional. An explicit `--output-format` from the caller wins, and a non-claude command is
spawned untouched. A command reaching claude indirectly (`bash -c "claude …"`) is not detected
and does not need to be; SKILL.md spawns claude directly.

*Rotate, don't truncate.* The proposal said `:> "$log"`, which is half right — a reused id must
not inherit an old mtime, but truncating destroys exactly what crash triage needs. `_rotate_log`
moves the previous transcript aside under a timestamped name instead. That also closes the other
half of the evidence: four lane logs in build 2 stacked two to four sessions each, which is why
several of that run's session boundaries are unrecoverable.

*Verified against the real thing,* not just stubs — Claude Code 2.1.220, a live
`claude -p --output-format stream-json --verbose`. The event shape the renderer assumes
(`.message.content[]` with `type: "text"`, and a final `result` carrying `subtype` / `is_error`)
is what the CLI actually emits, and the renderer produced correct prose from that capture. The
stream also carries a `rate_limit_event` type, which is a free lead for P14.

**No SKILL.md change.** Lane logs still read as text and `lane-status` still answers the same
three states, so nothing a wave must *decide* changed — the machinery carried all of it.

## P14 · Handle usage limits deliberately instead of waiting them out

**Evidence.** `wave-20260721-210534.log` is one line — *"You've hit your session limit · resets
10pm (America/Chicago)"* — and the next wave starts 22:04:05. **57m35s dead, a quarter of the
run.** `usage_limit: downshift_model` is documented in `references/loom-config.md` but
nothing implements it, though `claude --fallback-model` is exactly that primitive.

**Fix.** Wire up the downshift, and since the wave is told the reset time, have it install a
one-shot wake for that moment instead of relying on polling.

**Implemented 2026-08-01, with P15** — they are the same code path (what happens when a wave
exits nonzero), and the first thing that path has to decide is *which* of the two it is looking
at. A usage limit retried as a crash spends a session to be told the same thing, which is
precisely what the observed run did.

**The reset time is machine-readable, and P13 is what put it in reach.** A streamed session emits
`rate_limit_event` carrying `resetsAt` as an epoch. So the wave is streamed like a lane now, and
the pause reads the epoch directly — no parsing "resets 10pm (America/Chicago)" out of prose, and
no timezone guessing. A limit with no readable reset falls back to a fixed 15-minute re-check
rather than a guessed clock time: one skipped tick is the whole cost of being wrong, where a
misparsed timezone is hours.

**The false positive is the real hazard, and it is not hypothetical.** A live capture of a
two-word session contains a `rate_limit_event` with `status: "allowed"` — healthy runs emit
these. Pausing on the event's presence would stall a working build, so the *failed session* is
the trigger and the event only supplies the time. There is a planted-violation test for exactly
this, because it is the failure mode that would be worst and quietest.

**What the three policies now do.** `pause_and_resume` (default) pauses until the reset and lifts
itself; `stop_and_wait` pauses and stays paused until `tick.sh resume`; `downshift_model` passes
`--fallback-model` to waves *and* lanes. The `usage_pause` / `usage_resume` ntfy events were
already named in `references/loom-config.md` and had nothing emitting them — they do now,
carrying the reset time, which is the whole of the human-facing fix.

**Correction to this proposal's premise.** `claude --fallback-model` is *not* documented as a
usage-limit primitive: CLI 2.1.220 says "when the default model is overloaded or not available".
Whether a five-hour usage limit counts as "not available" is unverified, and verifying it means
hitting a real limit. It is wired because it is cheap and it is the right primitive if it does
apply — but the pause deliberately does **not** lean on it working. Anyone revisiting P14 should
treat "downshift rescues the run" as an open question, not a settled one.

**What is deferred with P3.** "Install a one-shot wake for that moment" needs launchd, which is
not in use. In a tick-driven build the pause still does the load-bearing work: ticks during the
blackout spend no session, the notification tells the human when to come back, and the first tick
after the reset resumes automatically. The one-shot wake would only remove the need to tick by
hand at that moment.

## P15 · Give crashed waves diagnostics and one retry

**Evidence.** Three logs contain exactly `Execution error` and nothing else, 15 bytes each:
`wave-20260721-203244.log`, `lane-gate-17-r1.log`, `lane-impl-13-r2.log`. Cost was 4m51s of
wave plus two lanes, after which W4 had to re-derive all state ("No lanes were registered at
wave start"). A crashed lane at least still fires the next tick — the `nohup` wrapper does so
regardless of exit code (tick.sh:120) — but a crashed wave just sets `exit 1` and waits.

**Fix.** Capture stderr separately, retry once with backoff, and notify after N consecutive
wave failures.

**Implemented 2026-08-01, with P14** (see there for why they are one change). All three parts
landed as written.

*Separate stderr* is the part that actually explains the evidence. Those three logs were 15 bytes
because stdout and stderr were merged into one file and the session died before writing anything
to stdout. They are separate now — `wave-<ts>.log` for the transcript, `wave-<ts>.err.log` for
the error — so a wave that produces no transcript at all still leaves the reason next to it.

*One retry* is asserted **on the nose**, not as a lower bound: a retry loop that never gives up is
its own failure mode, so the test counts wave invocations and requires exactly two. A transient
failure recovers inside the same tick; what survives the retry increments a consecutive-failure
count and, at `crash_cap`, pushes `build_halted` with the head of the error. A good wave clears
the count.

No new config key: `crash_cap` already means "how many crashes before escalating", and P21's rule
says a key must earn its place. The backoff is a constant with an `LOOM_RETRY_BACKOFF_SECONDS`
test seam.

**A test-design note worth keeping.** The first version of P13's liveness test used a
zero-minute staleness window, which made it turn on sub-second timing and fail roughly one run in
four. The scenario being modelled is a lane *40 minutes* into real work, so the real 30-minute
window is also the honest one — and the polling loop that waits for a lane's stream now fails
loudly when the stream never appears, instead of falling through and reporting the symptom
(`stale`) of a completely different problem.

## P16 · Fix the probes so they actually probe

**Scope note (corrected 2026-08-01).** The run had *three* probes, not two. The E11 probe
succeeded: `wave-20260721-221123.log:3` records a real `crucible serve` against the live Railway
target, exercising the dashboard end-to-end and cleaning up after itself. Only the E4 pair
failed, and they failed for two unrelated reasons. Epic acceptance is not broken as a concept —
one working probe is the evidence for keeping it.

**Evidence — attempt 1, the real P16 defect.** `lane-probe-e4.log` is a single line — *"I've
scheduled a fallback check in ~5 minutes and will otherwise be notified automatically when the
background task completes. Waiting now."* W10's diagnosis: *"it died having backgrounded a
command and tried to wait for a notification a stateless `claude -p` session can never get."*

**Attempt 2 — cause not established; two candidates, both real.** The retry reported *"Bash
denied every command touching the `crucible-probe-e4` worktree because it's missing a
`hasTrustDialogAccepted` entry in `~/.claude.json`"*. Tested on Claude Code 2.1.220
(2026-08-01), the trust mechanism is genuine: in an untrusted directory a headless
`claude -p --permission-mode dontAsk` prints *"Ignoring N permissions.allow entries from
.claude/settings.json: this workspace has not been trusted"* and the committed allowlist is
inert — every command then falls to the auto-mode classifier, which denies most of them. But
trust **does cascade from a parent directory entry**: the same run inside
`Projects/crucible-64-endpoint-fixes` — no entry of its own, parent `Projects` trusted — emits
no warning and loads the allowlist. Since `crucible-probe-e4` also lived under `Projects`, the
trust explanation only holds if the `Projects` entry post-dates the probe, which the JSON does
not record. The competing explanation is the lane-cwd `cd` gap in P4. Both are cheap to close;
close both rather than arguing the history.

**Fix.** Probe prompts must block on commands directly rather than awaiting notifications
(attempt 1's defect, unambiguous). For attempt 2, take P4's allowlist validation *and* have
worktree creation assert trust — either an entry for the worktree or a trusted ancestor. Assert,
don't blindly write: the parent entry usually already covers it.

**Trust half implemented 2026-08-01.** The assertion
lives in `spawn-lane`, not bootstrap: bootstrap runs once in the repo root before any worktree
exists, and worktrees are *siblings* of the repo, so a repo trusted only by its own entry says
nothing about them. At spawn time the lane's directory is already in hand. `_nearest_trust`
walks it upward through `~/.claude.json` (seam: `LOOM_TRUST_FILE`) and the **nearest** entry
wins either way — a directory whose own entry is `false` is refused even under a trusted parent,
since someone declined that dialog deliberately. Whether Claude Code itself resolves that case
the same way is unverified; this is the conservative reading, and it fails loudly rather than
burning a session. The refusal names the ancestor to trust. Nothing is ever written: granting a
directory blanket auto-approval stays the human's call.

**Prompt half implemented 2026-08-01.** SKILL.md step 6 was three lines — "spawn a probe
session" — and that vagueness is the defect: the prompt was improvised each wave, and one
improvisation backgrounded a command and waited for a notification. Step 6 now carries an
explicit four-rule contract the wave must write into every probe prompt: every step blocks (a
headless session has no notifications, no wake-ups, no callbacks); a background stack is
*polled* with a hard attempt cap, never awaited, and cap exhaustion is a probe failure to
report rather than a reason to keep waiting; the stack is torn down before the lane exits; fix
tickets and the epic-issue result are the final act. It also states what the E11 probe modelled
— exercise the epic as a *user*, against a really-running stack, not the test suite again.

Polling needs tools, so the generated allowlist gained `BashOutput` and `KillShell` (plus the
legacy `KillBash`), verified present in the installed CLI 2.1.220. Without them a probe can
neither read its server's output nor stop it, and the lane outlives its own stack. `curl` and
`sleep` were already there from P22. One thing the contract cannot fix: no spawned session may
run `rm`, so probes are told to leave ephemeral files where they fall rather than attempt
cleanup — the same gap P17 owns.

Step 6 now says probe *lane*, which lands the probe half of P5's "never inline wave work". P5
stays open for the merge queue and the lock split, which are the larger part of it.

**Two things the trust work shook out.** jq's `//` treats `false` as absent, so the first version walked
straight past a declined directory to its trusted parent — the planted-violation test is what
caught it. And on this machine `~/Projects` is trusted, so the cascade already covered
`crucible-probe-e4`, which has no entry of its own; the attempt-2 diagnosis therefore holds only
if that parent entry post-dates the probe, which `~/.claude.json` still does not record. The
history stays unresolvable — the check is now cheap insurance for a repo on a fresh path, which
is exactly P22's zero-setup case.

## P17 · Give each wave its own scratch files

**Evidence.** `wave-20260721-232712.log:13` — a write to a stale `/tmp/wave-note-16.md` left by
an earlier wave *"failed silently-into-the-wrong-content — the follow-on `glab api` post picked
up that old file's content and posted it as a comment on #16 before I caught it."* A correction
comment had to be posted.

**Fix.** Per-wave unique scratch paths.

**Implemented 2026-08-01.** Every session — wave *and* lane — is handed `$LOOM_SCRATCH`, a fresh
empty directory under `$LOOM_HOME/scratch`. Uniqueness is `mkdir` itself, not a clever name:
`mkdir` fails if the path exists, so the helper retries with a suffix until it wins, and two
sessions starting in the same second cannot collide. Re-running a lane id gets a new directory
too — the test that matters is the planted violation, a second run under the same id seeing an
empty directory rather than the first run's files.

`tick.sh` creates it because no spawned session may run `mkdir`, and prunes directories older
than 7 days on each tick because no spawned session may run `rm` either. The prune is scoped to
`$SCRATCH_ROOT` and guarded against an empty, `/`, or `$HOME` root, with a test for the guard —
it is the one line here that could delete a home directory if it ever went wrong.

This also closed the two referrals from today's work: P4's long-note file (which briefly had its
own `$ORCH_NOTES` directory, now folded in — one variable, not two) and the probe contract's
ephemeral files, which now go to `$LOOM_SCRATCH` and are simply left there.

## P21 · Delete or implement the config keys nothing reads

**Evidence.** `tick_interval_minutes` is canonical in `references/loom-config.md` but
`cmd_install` hardcodes `${1:-900}` and never consults the config — and crucible's own
`.loom.yml` omits the key entirely. `usage_limit: downshift_model` has no implementation
(see P14).

**Fix.** Wire them up or remove them. A setting that silently does nothing is worse than no
setting.

**Deciding which — default to removal.** A key survives only if it passes all three:

1. Would two real repos set it differently?
2. Can the right value not be derived?
3. Has anyone actually wanted to change it?

Fail one and it is not a setting — it is a constant with extra steps, or an unwritten
derivation. This is constitution rule 4 (*every artifact has a consumer*) applied to config, and
under P22 the bar rises again, because every surviving key is a decision paid on every new repo.
The asymmetry justifies the default: deleting a dead key is free and reversible — add it back
when a real failure demands it, per rule 3 — while wiring one up costs implementation, tests,
docs, and a permanent decision for every future repo, all spent on speculation.

**Resolution — `tick_interval_minutes`: removed** (2026-08-01). Fails all three. Once P1 makes
the self-trigger reliable the timer is a pure backstop for two events — the initial kick and
post-stall resume — and no repo needs a different backstop. `cmd_install`'s 900s was already
correct behaviour; the docs were the bug. Key deleted from the config reference, and the
constant annotated in `cmd_install` so the next reader does not "fix" it back into a key.

**Resolution — `usage_limit: downshift_model`: wire it up**, owned by P14. It passes all three,
and P14 supplies the evidence the rule asks for: 57m35s of dead time in one run, a quarter of
the whole build, with `claude --fallback-model` already the exact primitive. The choice between
pausing and downshifting is a genuine cost-versus-throughput preference that cannot be derived.
Under P22 it belongs in the global layer, beside P18's model map. Note this is the opposite call
from its sibling key — the rule is a test, not a bias toward deletion.

Note that fixing P1 lets the heartbeat interval get *longer*, not shorter — a correct coalescing
trigger makes the timer a true backstop.

## P22 · Make a new repo zero-setup

Adopting the skill on a new repo is a project before the project. Every artifact it needs is
hand-authored, and the build cannot start until all of them exist.

**Evidence.** SKILL.md's "New repo bootstrap" requires, before wave 1: `.loom.yml`,
`scripts/gate.sh`, a committed `.claude/settings.json`, six tracker labels, and a CI pipeline —
emitted as a repo-bootstrap epic "and everything else blocks on it." Crucible's own
`.loom.yml` is 55 lines, 26 of them settings. Two of those artifacts have already
failed in the field: the hand-written allowlist broke the `api` gate (P4) and is a live
candidate for the probe denial (P16), and workspace trust cost a probe attempt outright.
Nothing about that setup is interesting work, and none of it delivers a requirement.

**Fix.** Three layers, and the human writes only the third.

**Layer 1 — global preference, `~/.loom/config.yml`.** Machine- and person-level, not
repo-level; identical across every repo. `max_lanes`, `crash_cap`, `rejection_cap`,
`heartbeat_stale_minutes`, `usage_limit`, the ntfy push-event list and topic prefix, and the
per-lane-type model map (P18, currently specified nowhere). Written once, ever. `usage_limit`
carries the `downshift_model` option that P21 kept and P14 implements; `tick_interval_minutes`
is not on this list because P21 deleted it.

**Layer 2 — derived, no file.** Everything discoverable by reading the repo:

| Key | Derivation |
|-----|------------|
| `base` | `develop` if it exists on the remote, else `main` — SKILL.md *already states this rule*, so it should never have been a key |
| `gates` | stack pack keyed on `uv.lock` / `package.json` / `go.mod` / `Cargo.toml` → literal commands per tier |
| `runner` | convention: `scripts/gate.sh`, generated from the resolved `gates` |
| ntfy topic | global prefix + repo name |
| tracker labels | the six names are fixed; create them on first run |
| allowlist | universal base (`git`, `glab`, `tick.sh`, file tools) + the stack pack's commands + the worktree mechanism |
| worktree mechanism | repo-detected, as today (`openemr-cmd` vs plain `git worktree`) |
| workspace trust | assert an entry for the worktree *or any ancestor* (P16); the parent usually covers it — implemented at `spawn-lane`, not bootstrap, because worktrees are created later and are siblings of the repo |

Stack packs emit **literal commands**, never abstract tokens — that is the openemr lesson
already recorded in `references/loom-config.md`.

**Layer 3 — repo-specific, `.loom.yml`.** Only facts about the world outside the repo,
or about intent, which no detector can infer: environment variables the gates need
(`CRUCIBLE_LIVE=1`), a live target URL, out-of-band services. For crucible this is roughly three
lines instead of fifty-five. The file becomes optional — its absence is a valid, complete
configuration.

**Resolution.** Each key is first-hit of repo → derived → global → built-in default; the repo
layer may override anything, including a derived gate suite. `tick.sh resolve-config` emits the
merged document so the effective config is inspectable in one command rather than reasoned
about — the same move as P7's snapshot. This does not weaken the no-shadow-state rule: config
at every scope is read-only input, never build state.

**No new verb.** Resolution and bootstrap fold into `start`, which already exists and is already
idempotent. Adding an `init` verb would add a step to the very sequence this proposal exists to
shorten. `start` generates what's missing, asserts trust, creates absent labels, and reports the
one or two things only the human can supply.

**Acceptance test.** A fresh repo containing nothing but source and a PRD reaches wave 1 with
zero hand-authored configuration files. Anything that fails that test is the next item of work.

**Implementation notes — derivation engine.** `tick.sh resolve-config` implements the full
precedence chain and prints the merged document with each scalar's source; `cfg()` now reads the
global layer. Derived today: `base`, the `gates` pack from stack detection (uv / poetry / python
/ pnpm / yarn / npm / go / cargo, with integration and e2e tiers appended only when their
conventional marker exists), `runner`, and the whole permission surface, written by
`tick.sh install-settings` (idempotent; refuses to clobber a differing hand-edited file without
`--force`). 19 new tests, 51 passing. Crucible resolves unchanged, and its
`CRUCIBLE_LIVE=1 uv run pytest` now generates `Bash(CRUCIBLE_LIVE=1 uv *)` — the exact rule
whose absence cost a completed gate review its verdict.

**Implementation notes — bootstrap.** `scripts/bootstrap.sh` is the write half, split from
`tick.sh` rather than eroding its read-only charter (which `tick-test.sh` enforces by scanning
argv). It seeds `~/.loom/config.yml`, writes the settings surface, and creates the five
missing ticket-state labels — all idempotent, nothing ever deleted. It is wired to **`tick`, not
`start`** (operator preference: `tick` is the verb actually used, and tracker writes should not
be a side effect of starting a build): the first tick in a repo runs it behind a sentinel in the
state dir, a failed bootstrap writes no sentinel so the next tick retries, and it never blocks
the wave. The ntfy topic now derives as `<global topic_prefix><repo name>`, layered like every
other key. 64 tests passing.

**Acceptance test passed 2026-08-01** against `jordanphillips/orchestrate-test`, a real GitLab
project with zero labels. A bare uv repo — source, tests, a PRD, and no `.loom.yml`, no
`.claude/settings.json`, no `scripts/gate.sh` — went from clone to a running wave with nothing
hand-authored. `resolve-config` derived stack `uv`, `base: main` (no `develop` on the remote, so
the fallback was exercised for real), and the four gate tiers; the first tick wrote the settings
surface, created all five labels, and launched the wave; the second tick skipped bootstrap and
left the labels untouched.

The run surfaced one defect stubs could not: the generated `.claude/settings.json` was
**uncommitted**, and a lane worktree is created from `origin/<base>` — so the allowlist existed
in the base clone and nowhere the work happens. `bootstrap.sh settings` now warns when the file
is uncommitted. It warns rather than committing: an allowlist entering history is a security
surface and the human's call.

**Interactions.** P4's allowlist *validation* becomes allowlist *generation* — a generated
allowlist cannot mismatch the gate commands it was generated from, which closes the defect
rather than detecting it. P21's dead keys should be resolved before this lands, so no key gets
carried into a layer nobody reads. P18's model map has no home today and gains one in layer 1.

## P23 · Make the evidence for the next round fall out of running a build

Every number in this file — 3h50m for six tickets, 35.3% of wall clock inside wave sessions, the
57m35s blackout, peak concurrency of 2 against `max_lanes: 4` — was reconstructed **by hand** from
31 raw transcripts plus filename arithmetic. None of it survives to the next build. So
improvements stayed anecdotal, no change could be shown to have helped, and the next round of
analysis would start from zero.

**Fix.** `tick.sh` appends one JSON line per significant event to `events.jsonl`; `tick.sh report`
aggregates it, and `report --ticket <n>` traces one ticket's whole journey with the log path to
read next. Both views read only that file, so a report costs no tracker calls and works long after
a build is over.

**Implemented 2026-08-01.** Three rules keep it honest, and each is load-bearing:

*The machinery writes it, never the model.* `tick.sh` already sees everything worth recording — it
spawns the lanes, runs the waves, takes the merge lock, writes the pause. A model-written log goes
missing exactly when a wave crashes, which is the moment it is needed. The test that states this is
a wave that dies still leaving its start, end and exit code.

*Write-only from the loop's point of view.* Nothing in a scheduling decision reads it. A wave that
consulted `events.jsonl` would make it shadow state and break constitution rule 1. There is a
planted violation for this: a grep asserting nothing outside `report` even opens the file.

*It survives builds.* Every line carries the build label, so build 3 is measured against build 2
rather than replacing it. The label is cached when a snapshot resolves it — purely to tag records,
never to decide anything.

**Ticket history without observing label changes.** `tick.sh` never sees a transition, so each
snapshot emits the whole open-ticket state map. A ticket first seen in `review` entered review
around then; one absent from the final map closed. Resolution is the wave cadence — approximate,
honest, and enough to compute cycle times that previously did not exist at all.

**It found a real race on its first run.** Adding an event between the merge-lock reserve and the
stamp made a pre-existing bug deterministic: a merge lane with a fast command finishes and releases
the lock *before* the parent stamps it, so the write hit a directory that no longer existed —
fatal under `set -e`, so `spawn-lane` reported failure for a lane that ran fine. Worse, had another
merge reserved in between, the stamp would have overwritten *its* ownership with a dead pid. The
lane now stamps the lock itself as its first act, which closes the window rather than narrowing it.
An instrumentation change surfacing a concurrency bug is the proposal paying for itself before it
has produced a single report.

**The same jq trap, twice.** `$p[.+1] | tonumber? // (fromjson? // $p[.+1])` — the pipe rebinds `.`
to the value, so the fallback evaluated `"<value>" + 1` and every event silently failed to write.
Identical in shape to the `startswith` bug in P11. In this file, bind before you compare or fall
back; never lean on `.` inside a piped alternative.

**What it deliberately does not capture.** Why a wave chose what it chose. That stays in the
transcript and in the Build-issue lessons thread, which records the *why* in prose. This records
the *what* in numbers. Neither replaces the other.

## P25 · Give the skill a maintenance verb that does not trust its own tests

The skill is 4,212 lines of machinery with no maintenance path. The 2026-08-01 review round is the
receipt: four independent readers found **14 defects in the scripts and 12 in `SKILL.md`**, against a
suite that was green at 71 tests. Fixing six of the confirmed findings then introduced five more.
None of that was reachable by running the tests, and none of it would have happened without someone
deciding, by hand and on the day, to go looking.

**Fix.** A `qa` verb: fan out one reviewer per file, confirm every finding against the real code,
report, and stop. Run by a human, never by a wave.

**The suite is the primary suspect, not the evidence.** Note what the inventory says:

    tick-test.sh   1770 lines   largest file in the skill — never independently reviewed
    tick.sh        1698         reviewed 2026-08-01
    SKILL.md        429         reviewed 2026-08-01
    bootstrap.sh    181         reviewed 2026-08-01
    references/     134         never reviewed

The biggest file is the test suite, it is the one file no reviewer has read, and it directly caused
three of the worst findings of the round: an assertion that called `ok` in **both** branches, a
fixture that planted a single verdict so ordering was never exercised, and a graph fixture that
happened to contain an unblocked ticket. A green suite is not evidence — it is a claim by the least
scrutinised file in the skill.

Two rules follow. `tick-test.sh` gets a reviewer of its own, briefed to find assertions that cannot
fail, fixtures that cannot distinguish the guard from its absence, and planted violations that are
not actually planted. And when a reviewer finds a bug the suite missed, that is a test gap: the fix
is not done until a test fails without it.

**Fan out per file, with a brief.** One agent reading 4,212 lines skims. Every finding on 2026-08-01
came from a reader with one file and a narrow question. Keep that shape, and give
`references/loom-config.md` and `references/ticket-template.md` their first reader.

**Confirm before reporting.** Reviewers produce claims, not findings. Each one is reproduced against
the real code or dropped before it reaches a human — an unverified list spends the reader's
attention on false positives, which is worse than no list. `qa` reports only what survives.

**It reports; it does not fix.** A maintenance verb that rewrites the machinery unattended is how a
working loop gets broken, and the five defects introduced by 2026-08-01's own fixes say the repair
step needs supervision. Fixing is a separate, approved action. Same staging rule as `plan`.

**Include a read-only live check.** `graph` reporting the wrong opening width was caught *only* by
running against the real tracker — out-of-build blockers were being dropped, and no fixture in the
suite could have shown it. `snapshot`, `graph`, `lane-status` and `report` against a live repo are
cheap and catch the class of bug fixtures structurally cannot.

**Keep it out of the wave's context.** `SKILL.md` loads on every wave and QA never runs during a
build, so the body belongs in `references/qa.md` with at most one routing line in the verb table.
Constitution rule 4 — every artifact has a consumer — puts the output in two places: the human who
ran it, and a dated review-round section appended to `PROPOSALS_ARCHIVED.md`, following the
2026-08-01 precedent there.

**No herdr dependency.** Herdr was how the 2026-08-01 round happened to be driven; the brief is what
made it work. Subagents do this identically, and a maintenance verb must not require a particular
terminal to be usable.

**Honest scope.** The deliverable is mostly a written brief — the per-file reviewer prompts, the
green-suite rule, the confirm step — not executable machinery. That is still worth building: right
now it exists only in one session's context and a scratch file, and it is the only thing that has
ever found a defect in this skill.

**Implemented 2026-08-01.** `references/qa.md` carries the brief; `SKILL.md` gains one table row
and a four-line stanza that routes to it. No machinery — the verb runs existing commands and
subagents.

**What would falsify this.** If a `qa` round on code already reviewed comes back with nothing that
survives confirmation, the verb is ceremony and should be dropped rather than kept as ritual. Run it
once against the current tree, which has had four reviews and one verification pass, and see.

## P26 · Turn a finished build into next round's proposals

P23 made a build leave numbers behind. Nothing yet turns those numbers into a decision. Every entry
in this file came from a human reading raw transcripts on a spare afternoon — which is why there is
exactly one analysed build on record, months of runs after the loop started working.

**Fix.** A `retro` verb: read the last build's events, explain what the time was spent on, and append
proposal-shaped entries to this file for whatever it found. Human-run, after `build_complete`,
read-only on the tracker.

**`report` computes; `retro` explains.** The division matters or the two verbs collapse into each
other. `report` already emits span, wave/lane/blackout shares, wave and lane counts, peak
concurrency, lanes by type, rc-7 rejections, crashes, and skipped-vs-replayed ticks — deterministic
aggregation, no model involved. `retro` calls it rather than recomputing it, and spends its effort on
the question events cannot answer alone: *why*. That means joining numbers to lane transcripts, which
is a fan-out — one reader per suspicious lane — not one agent reading 31 logs.

**Its output is a proposal, not a fix.** The instinct is to hand findings to an agent that repairs
them. Do not: six confirmed fixes on 2026-08-01 introduced five new defects, and unattended edits to
the machinery are how a working loop breaks. `retro` writes into this file — problem, evidence with
numbers, proposed fix, falsification test — and the tracking table already provides the intake and
the status discipline. A human picks what gets built. Constitution rule 4 is satisfied because the
consumer already exists.

**Five things it must compute that nothing computes today:**

*Why lanes sat idle.* The highest-value output. Build 2 peaked at 2 concurrent lanes against
`max_lanes: 4` — half the capacity never used, and the reason was never established. The candidate
causes are distinguishable and have entirely different fixes: no ready tickets because the graph is
too narrow, the lane cap, the merge lock held, a usage pause, or everything sitting in review.
Attribute idle lane-slots to those buckets and the next proposal writes itself.

*Rework as a share of lane time.* Lane-seconds that produced nothing: gate retries (`gate-N-r2`,
`-r3`), rc-7 rejections, crashed lanes, retried waves. `report` counts these; retro should price them.

*Wait versus work, per ticket.* A ticket open three hours with forty minutes of lane time has a
queuing problem, not an implementation problem — and that distinction decides which proposal is worth
writing. Both halves are already in `report --ticket <n>`; nothing yet takes the ratio across all
tickets.

*Actual critical path against the predicted one.* `graph` computes `critical_path` before the build
(P8). Retro can check whether the chain that actually set the build length was the predicted chain,
which validates or falsifies the graph model. And if one chain accounts for nearly the whole span, no
other finding matters that round.

*A baseline, or an explicit admission there is none.* Every event carries a build label precisely so
build 3 can be measured against build 2 instead of replacing it. Without a comparison "slow" is
unfalsifiable. The first retro has no prior build and must say so rather than invent a standard.

**One discipline, or this becomes an essay.** Every claimed inefficiency carries a number and a
falsifiable fix. A model handed a table of timings will always find a narrative; the number is what
separates a finding from a plausible story. Anything that cannot be stated as "X cost N minutes, and
here is the change that would show up as N minutes saved next build" is dropped, not softened.

**Honest limits.** Ticket state transitions are sampled at wave cadence, so every per-ticket timing
is ±one wave and must be presented that way. And events record what happened, never why a wave chose
it — the reasoning lives in the transcripts and the Build-issue lessons thread, which is exactly why
retro has to read them rather than working from `events.jsonl` alone.

**Relationship to P25.** `qa` reviews the code; `retro` reviews the run. Keeping that boundary sharp
stops either from growing into a general-purpose "look at everything" verb that does neither well.
Both are human-run maintenance, so both belong in `references/` with one routing line each, out of
the wave's context.

**Implemented 2026-08-01.** `tick.sh retro [--build <l>] [--vs <l>]` computes the four analyses;
`references/retro.md` says how to read them and how to write the proposals; `SKILL.md` gains one
table row and a five-line stanza. Suite 183 → 192.

The enabler was extending the snapshot event with `deps`, `ready`, `impl_free`, `max_lanes`,
`gateable` and `merge_in_flight` — and moving its emission so it is derived from the **finished
snapshot** rather than recomputed from the raw payloads. A second implementation of "which tickets
are ready" would drift from the one the scheduler actually used, which would quietly invalidate
every conclusion drawn from it.

**A missing field is not a zero.** The first live run reported `at capacity 100%` for a build where
nothing had run at all: snapshots written before this record carry no `impl_free`, and `// 0` read
that as "no free slots". Unknown time is now its own line rather than being distributed into a
bucket, and that defect became the section's planted violation — the fixture strips the field and
asserts the time lands in `unrecorded`. Found by running it, not by the suite, which is the same
lesson as the graph width bug in P8.

**What would falsify this.** If retro's first pass produces only findings already in this file as
open proposals, then reading the numbers adds nothing to reading the code, and the verb should be
dropped. The first build after P23 is the test — and it is the same build that tests P24.

## P24 · Let a human watch a lane while it runs (part A — archived 2026-08-02; part B open in PROPOSALS.md)

A running lane is effectively invisible. P13 made the machinery able to tell busy from dead, but it
did nothing for a person: `lane-status` gives a pid and a word, and for a claude lane the `.log`
holds only stderr until the lane exits. The readable transcript is rendered by the exit epilogue, so
the only way to follow live work today is to read raw `lane-<id>.jsonl` by hand. During a build the
honest answer to "what is ticket 14 doing right now" is "wait for it to finish, then read the log".

**The tempting fix is the wrong one.** Herdr can host a coding agent in a visible pane, so the
obvious move is to stop spawning detached headless sessions and launch each lane as a pane agent
instead. That trades away more than it buys, and every item below is load-bearing machinery this
file already paid for:

*The exit code disappears.* A headless `claude -p` lane exits with a number; an interactive pane
agent never exits, it goes idle and waits. `.rc` files, **exit code 7** for a gate's mechanical
rejection (P11/P12), the `lane_exit` event behind `report` (P23), and the self-trigger tick that
keeps the loop moving (P1/P2) all read that number. Replacing it with "the pane went idle" means an
agent that stalled confused is indistinguishable from one that finished — herdr says as much
directly: `unknown` does not prove completion. That is the model reporting its own outcome, which
is exactly what P23 was designed to avoid.

*Lanes stop being detached.* `nohup` means a lane outlives the wave that spawned it, the released
lock, and the closed terminal. A pane process dies with its herdr session.

*Approvals block instead of proceeding.* Headless lanes run under the generated allowlist so nothing
stops to ask. An interactive pane agent stops and asks — good when someone is watching, fatal
when nobody is, which is the normal case.

*Panes do not scale to a wave.* Several implementers plus gates plus a merge is an ordinary wave.
Splitting a terminal that many ways produces columns nobody can read.

*It costs portability.* `/loom` would only work when driven from inside a herdr session on a
machine with herdr installed.

**Fix, part A — a follow mode for the renderer.** Lanes already stream to `lane-<id>.jsonl` live;
`render-log` is simply one-shot. Add `render-log <id> --follow`, which renders new events as they
arrive and exits when the lane's pid is gone and the stream is drained. Then a window onto a lane is
just a command, and herdr is only one way to get a window — a bare terminal works identically:

    herdr pane split --current --direction right --cwd "$PWD" --no-focus
    herdr pane run <pane> "tick.sh render-log impl-14 --follow"

Execution semantics do not move at all. Viewers open and close while the build runs, a killed viewer
costs nothing, and a lane spawned before anyone decided to watch can still be watched.

Two constraints make it safe. **A viewer writes to stdout, never to the log** — the exit epilogue
owns `lane-<id>.log`, and a follower appending to it would corrupt the artifact it is watching.
**Any number of viewers on one lane is fine**, because following is a file read and nothing more; a
viewer must never take a lock, touch a pid file, or write an event.

**Fix, part B — an opt-in supervised lane.** Part A is read-only, which leaves one real gap: a
wedged lane can currently only be killed. You cannot answer its question or redirect it. A
`spawn-lane <id> --supervised` would run the session interactively in the foreground of the current
terminal instead of detaching it — the debugging case, one ticket at a time.

This is a human verb and the wave must never emit it. It also needs two guards, because a supervised
lane's exit code records when a person closed the session, not how the work turned out:

- Its `.rc` must not feed any automatic path — no self-trigger, no rc-7 verdict. Resolve it by hand
  with `clear-lane` or an explicit verdict comment.
- `--supervised` and `--merge-lock` are mutually exclusive. A human who wanders off mid-merge would
  otherwise hold the queue until staleness breaks it.

**Order.** Part A is small, safe, and useful on its own; part B is worth building only if watching
turns out to leave a real intervention gap. Do A, run a build, then decide.

**Invocation.** `watch` already exists as a verb and is the entry point; no new verb is needed. It
keeps its current job — the aggregate, tracker-aware picture that raw transcripts cannot give — and
gains the panes:

- **In herdr:** print the status snapshot, then launch the pane-opener detached and return. Because
  it is detached, the panes outlive the `watch` session; no Claude session sits there holding them
  open. Same shape as a lane.
- **Outside herdr:** the snapshot, plus one line saying panes are available from a herdr session.
- **`watch --no-panes`:** snapshot only.

Handing the human a command to copy is not the design. They asked to watch; watching is what should
happen.

**The accessory, and the rule it must not break.** The pane-opener is a standalone script that polls
`lane-status` — it is never called by the machinery, and it does not register with `spawn-lane`. If
it did, `tick.sh` would have to know herdr exists. The test that keeps this honest: **delete herdr
from the machine and nothing about a build changes.** You lose the panes; `render-log --follow`
still works in any terminal, and so does `tail -f`. Compare the rejected design above, where
deleting herdr means no lane can run at all.

Its four design decisions: panes are **reused, not accumulated** (a finished `--follow` leaves the
pane at a prompt for the next lane, which is what stops a long build ending in thirty panes); it
**polls rather than hooks**; it **leaves panes open** when stopped, since the last output is often
what you want; and it **refuses to run outside herdr** rather than degrading into something
confusing. Default cap is four — four readable panes beat nine unreadable ones.

**Part A implemented 2026-08-01.** `render-log <id> --follow` renders the stream to stdout and
stops one full pass after the lane's process disappears, so what a lane writes on its way out is
not cut off. The renderer's jq is now shared between the one-shot and the follower, so a live view
and the saved transcript cannot disagree about what the lane said. `scripts/watch-panes.sh` carries
the pane-opener; `watch` gained `--no-panes`. Suite 192 → 202.

Four planted violations hold the design in place: the follower must not write `lane-<id>.log` (the
epilogue owns it, and appending would corrupt the artifact being watched); it must leave nothing in
the lanes directory and record no event; two viewers must be able to watch one lane at once; and
**`tick.sh` must contain no mention of herdr at all** — the last is a grep, and it is the test that
keeps the accessory from becoming a dependency.

Still unverified, because it needs a real build: how `pane run` behaves against a pane that is
mid-command, and a lane that appears and disappears between two polls.

**Part B remains open.** It was staged behind evidence deliberately — build it only if watching
turns out to leave a real intervention gap.

**What would falsify this.** If `report --ticket <n>` plus the rendered log after the fact answers
every question anyone actually asks, live viewing is a comfort feature and part A can wait behind
P18–P20. The first build after P23 is the test.


## P27 · Wedge detection counts progress, not bytes — and the watcher sees it

*(Rewritten 2026-08-02 from "Bound every session in wall-clock time" — same evidence, different
mechanism. Wall-clock caps were rejected: the skill already ruled "never an elapsed-total-time
check" because a fixed cap converts slow-but-healthy work into crash-count churn and half-pushed
branches. The two real defects the evidence shows are narrower: the staleness CLOCK was log
mtime, which retry chatter keeps fresh; and staleness ENFORCEMENT lived only in waves, which
were the thing that was dead.)*

A session wedged on a dead API stream ran until a wave noticed staleness — and in the
worst window, the wedged session was the only process alive, so nothing ever noticed.

**Evidence (build-1, overnight window 00:10–07:46).** Wave-000936 lived 1h36m. Wave-015558 lived
3h11m, of which **3h07m was four gaps of 27–77 minutes** between consecutive transcript events
where the next event is `assistant` — the model response itself taking that long to arrive, not a
tool running. Lane gate-1 crashed after 55m of "API Error: Connection closed mid-response";
gate-1-r2 spent **2h40m** (its second review subagent stalled) and exited rc 0 with no verdict.
Healthy rounds of the same gate took 228 s (r3) and 105 s (r4). Sessions wedged on the API
consumed roughly 7 of the build's 13h27m, and the staleness detector could not help: enforcement
runs in waves, and the wedged session *was* the only thing running.

**Fix (implemented 2026-08-02).** Three parts, no wall-clock caps. (1) **The liveness clock is a
per-lane progress stamp** (`<id>.progress`), maintained by the watcher's `quiet-tick`: a filtered
event count that excludes `api_retry` and `rate_limit_event` chatter, touched only when the count
grows — so its mtime means "last real progress", and both wedge shapes (silent gaps AND retry
chatter) freeze it. `lane-status` prefers the stamp over log mtime when it exists. (2) **The
watcher notifies** `lane_stale` / `wave_stale` once per incident — detection no longer requires a
live wave, and wave sessions (which previously had no staleness signal at all) get one. (3)
**Killing stays where it was**: waves harvest stale lanes (unattended recovery bounded by the
heartbeat interval), and the human decides in manual-drive — the watcher observes and notifies,
never acts, which is the covenant that makes auto-arming it acceptable.

**What would falsify it.** A wedge whose transcript keeps emitting genuine assistant/tool events
while accomplishing nothing — progress counting cannot see a *semantic* stall. If one occurs,
revisit bounded wall-clock caps as the backstop, per the original draft of this proposal.


## P28 · Make the brief file structural: `spawn-lane --brief`

Long prompts on the spawn command line fail at the CLI boundary, and the known fix — an untracked
brief file in the worktree — lives only in prose, re-derived by every wave that hits the wall.

**Evidence (build-1, 2026-08-01 23:42–23:46).** Eight impl-1 spawns died at the prompt boundary
in four minutes: an empty prompt produced "Hi! What are you working on today?"; a multiline
prompt was parsed as CLI options (`error: unknown option '- server/ (Python, uv, FastAPI), …'`);
one session received a fragment and asked "When do you want this to run?". Two of the build's
three counted crashes are this burst. The ninth attempt succeeded only after the wave invented
the brief-file technique by hand — now documented in the target repo's CLAUDE.md, but
`spawn-lane` still accepts any inline prompt, so nothing stops the next repo's wave from
repeating the burst.

**Fix (implemented 2026-08-02).** `spawn-lane --brief <file>` copies the brief into the lane
worktree as an untracked `.lane-brief-<id>.md`; the caller writes `-p @brief` and spawn-lane
swaps the placeholder for a fixed one-line pointer prompt. Inline arguments over **1000**
characters (`LOOM_MAX_INLINE_ARG`) are refused with a message naming `--brief` — 1000, not the
drafted 200, because the working short-prompt pattern ("fetch the ticket yourself") runs 400–600
characters and has never been denied; the cap sits near the observed failure boundary, not under
the observed success boundary. The sweep already treats untracked briefs as disposable
droppings, so teardown needs nothing new.

**What would falsify it.** A build with `--brief` in use that still produces dead-on-arrival
spawns — that would mean the boundary problem is permissions, not prompt length, and the fix
belongs there instead.

## P30 · Same-class rejection detection — design-decision block at 2, not cap-exhaustion at 3

One scheduling rule: a ticket rejected twice for the *same class* of defect
stops for a design decision instead of burning the cap on a third same-tier
guess. Today the only escalation is the rejection cap (default 3), which
spends every round before anyone is allowed to say "this is a design
question." *(Re-scoped 2026-08-03: the model-escalation half moved to P31,
where it belongs — it shares P31's spawn path, not this proposal's
scheduling rule.)*

**Evidence.** Build-3 #39 (2026-08-02): three gate rounds each correctly
fixed the exact variant in front of them — FIFO dispatch, then a single
scalar, then an arm counter — while the underlying class (position-based
turn-mark attribution) survived all three. The round-2 and round-3 gate
verdicts *already named the recurrence* ("same failure mode, one level
deeper"); the signal existed a full round before the cap tripped. The
eventual human decision ("key by turn identity; position and counters are
banned") took minutes and now also governs the sibling tickets — the
outcome the loop should have reached one round earlier.

**Fix.** The verdict template gains one line naming the defect class
(`same-class: <slug>`); each gate compares against the previous rejection
on the same ticket. On a match, the harvesting wave blocks the ticket for
a design decision at **2**. The cap stays as the backstop for rejections
that are merely *different* failures. Machinery: the verdict line,
snapshot surfacing consecutive same-class counts, one sentence in SKILL
harvest.

**Consumers.** The wave (it is a scheduling rule) and the human, who gets
the design question a round earlier.

**What would falsify it.** Same-class blocks firing on genuinely different
defects — the class line is too coarse; tune the slugs or drop it.

## P31 · Rework model escalation — manual `model::<tier>` label + automatic `rework_model`

One spawn-path feature, two triggers: which model does a ticket's next
implementation lane get? Manual — the human adds a `model::opus` /
`model::fable` / `model::haiku` label to the ticket (asked for
2026-08-03, watching rejections where one escalated round would likely
have beaten another same-tier retry). Automatic — a `rework_model` config
key (empty = same as `lane_model`) that implementation lanes use from
round ≥ 2, since late rounds are rare and self-select for hardness
(absorbed from P30 on re-scope, 2026-08-03: it shares this spawn path,
not P30's scheduling rule). The **override chain**, manual outranking
automatic outranking default:

    ticket `model::` label  >  `rework_model` (round ≥ 2)  >  `lane_model`

**Why a label for the manual half.** It is the only shape that satisfies
the constitution: tracker-resident (no shadow state — a fresh wave
reconstructs it, unlike a flag passed at spawn time), applied at the exact
UX moment the need is visible (reading the rejection in GitLab, one click
in the sidebar; or ask the driving session), persistent across rounds
until removed, and self-documenting for `retro`/P29 ("which tickets
needed the big model" is a label query priced by the cost dashboards).

**Why not just raise every lane's tier.** The 2026-08-02 lesson runs the
other way — every worker silently on the top tier was the *bug* the
`lane_model` key was added to fix. Escalation must be earned: by the
human's judgment (label) or by evidence of hardness (a rework round).

**Mechanics.** Bootstrap creates the three labels alongside the state set.
`resolve-config` surfaces `rework_model` with its source layer. `snapshot`
surfaces a per-ticket `model` field (null when absent; two `model::`
labels → take the highest, warn once). The fill/rework step resolves the
chain and passes `--model` when spawning that ticket's implementation
lane. **Implementation lanes only** — gates keep their own model;
escalating the reviewer because the implementer struggled is a different
decision, and one mechanism must not mean two things. The ticker renders
the escalation so the human sees it took:
`#46 — implementation started (opus)`.

**Consumers.** The wave (one chain resolution at spawn), the human (the
label sidebar), `retro`/P29 (escalation priced against outcome — including
whether `rework_model` earns its keep at all).

**What would falsify it.** Labels applied but never read (spawn path
missed a case → bug, fix); every ticket ending up labeled (the default
`lane_model` is wrong → fix the config, retire the labels); rework rounds
on the stronger model failing at the same rate as the base model (the
automatic half buys nothing → drop `rework_model`, keep the label).

**As implemented (2026-08-03).** Four labels, not three: `model::sonnet`
joins opus/fable/haiku, because with `lane_model` raised there is otherwise
no way to pin one ticket *down*, and the two-label tiebreak needs a total
order anyway. The chain is resolved in `snapshot` (`.model.{effective,
source}`) rather than reasoned out per wave — round number is derived, not
stored (`rejections.total > 0` is exactly "this round follows a rejection").
The ticker reads the model off the spawned command line rather than a
self-reported flag, so it can only ever show what actually ran. Two things
fell out: the bootstrap label table had to move from `:` to `|` separators
(a scoped label's name *contains* a colon, and all four would have been
created mangled), and the test suite turned out to read the developer's own
`~/.loom/config.yml` for every `cfg` lookup — now a fixture.

## P31 (adversarial tests) · Make the mandatory adversarial test a checkable deliverable

*Implemented 2026-08-07. Note the ID collision: rework model escalation, above, was
also filed as P31, and both are cited in the scripts. A `P31` about models, labels or
the escalation chain (`snapshot.jq`, `bootstrap.sh`'s label table, the model lines in
`tick.sh`) means that one; a `P31` about adversarial tests — the pregate rejection and
the two implementer brief lines — means this one.*

`references/ticket-template.md` asks every ticket for "Mandatory adversarial tests". The gate then
enforces that in prose, one expensive review round at a time.

**Evidence (seat-reservations build-1).** Five gate FAILs in the build. **Four were the same
family** — the mandatory adversarial test was not real, enforced coverage:

| Ticket | Round | Class the gate named |
|---|---|---|
| #2 | 1 | `missing-adversarial-test` |
| #2 | 2 | `adversarial-test-not-wired-to-gate` |
| #21 | 1 | `missing-adversarial-test` |
| #21 | 2 | `adversarial-test-skipped-in-ci` |
| #4 | 1 | `scope-creep` (the odd one out) |

Each round produced a *nearer miss*: absent → present but not on the tier's command list → on the
list but silently skipped in CI. Three rounds to converge on "the test must actually run." Total
rework was **11 lanes, 55m40s, 26.5% of all lane time**; #2 and #21 alone account for 5 gate lanes
and 5 impl lanes of it.

**Fix, in two halves.** *Ticket side* (`references/ticket-template.md`, this skill's own layer):
the section stops being prose and states the three conditions the implementer must satisfy — the
test is committed, it is **named in the tier's command list in `.loom.yml`**, and it is
demonstrated to fail when its subject is broken. *Pregate side* (`tick.sh --pregate`): when the
ticket body carries a non-empty adversarial-test section, check mechanically that the branch's diff
adds or modifies at least one file named in that tier's command list, and exit 7 if not.

That mechanical check would have caught three of the four — #2 r1, #21 r1, #2 r2 — at rc 7 in
seconds instead of spending **787s (13m07s)** of review-session time on `gate-2`, `gate-21` and
`gate-2-r2`. It cannot catch the fourth (`adversarial-test-skipped-in-ci`); judging whether a test
that runs actually asserts anything stays a review job.

**One limit worth recording, which is not a fix.** The `same_class_tail` ≥ 2 rule never fired,
because each round's gate coined a fresh slug for what a human reads as one problem. Here that was
the right outcome — round 3 passed on both tickets, so blocking at round 3 would have been strictly
worse. Do not tighten slug matching on this evidence.

**Reproduced 2026-08-06 in a second repo, in a shape the pregate half cannot see.**
ai-workout-generator-copilot build-1, first 20 gate verdicts: 13 PASS, 7 FAIL. **Four of the seven
are this same family** — and unlike seat-reservations, every one of the four *did* commit a test
that `pytest` already runs.

| Ticket | Class the gate named | What was actually wrong |
|---|---|---|
| #3 | `adversarial-test-mismatch` | test present, asserting a different thing than the bullet |
| #25 | `missing-adversarial-check` | one of the ticket's bullets had no test at all |
| #31 | `duration-budget-both-ends` | two-sided bound, only the upper half asserted |
| #5 | *(no slug — see below)* | boundary test written for `/api/plan`, not for `/api/plan/adjust` |

This is a different failure shape from the first build's. There the family was *absent → not on the
command list → skipped in CI*; the mechanical pregate check catches all three of those. Here the
test is committed, is on the tier's command list, does run, and passes — it just does not assert
what the bullet says. **The proposed pregate check would have caught none of the four**, because
"the diff adds or modifies a file on the tier's command list" is true for every one of them. The
four cost `gate-3` 201s, `gate-25` 291s, `gate-31` 253s and `gate-5` 370s — **1115s (18m35s)** of
review-session time, plus four rework rounds.

Note the pregate did not run at all in this build: `scripts/gate.sh` is itself a build-1 ticket
(#7, "Gate runner and CI"), and a missing runner is skipped rather than failed. So this build tests
the *ticket-side* half of the fix and says nothing either way about the rc-7 saving.

**What the second build adds to the fix — a third condition on the ticket side.** Committing a test
is not the deliverable; covering each bullet is. Require the implementer to state the mapping —
each bullet in `## Mandatory adversarial tests` → the name of the test function that asserts it —
in
the MR description, and to treat a bullet with no name beside it as unfinished work rather than a
lane note. That makes both omission (#25, #5) and partial coverage (#31, #3) visible to the
implementer before push, without asking a script to judge whether an assertion is meaningful. It
also stays inside this skill's layer: the section wording is `references/ticket-template.md`, and
the mapping requirement is one line in the implementer brief the wave already composes.

**And a named path for an unsatisfiable bullet.** #31's mandatory test was not skipped out of
haste — it is *unsatisfiable* against the constants ADR-0015 pins: the required band could not be
met for 162 of 166 accepted inputs. The lane diagnosed that correctly, disclosed it in both the
test docstring and the MR description, and deferred — and still spent a full gate round to be told
so. A bullet the implementer can prove cannot be satisfied should end the lane in `blocked` with
that proof, not in `review`. Cheap to state, and it is the one case where more rounds cannot help.

**One more limit, consistent with the first build's.** #5's FAIL verdict carried no `class=` slug
at all, so `same_class_tail` had nothing to match on. Two builds now show the same-class stop
failing to engage for two different reasons — fresh slug per round there, no slug here. Neither is
an argument for tightening slug matching; both are arguments for not relying on it as the backstop
for this family.

**What would falsify it.** A build where re-gate lane count does not drop, or where the pregate
check exits 7 on a branch the review gate would have passed — a false rc 7 is more expensive than
the round it saves. For the ticket-side half specifically: a build where implementers publish the
bullet-to-test mapping and this family still accounts for over half the rejections, which would
mean the gap is comprehension of the bullet rather than accounting for it.

**Final build-1 tally (ai-workout, 2026-08-07).** The build finished its run at 11 first-round
FAILs in 41 verdicts; the family held at 4 of 11 (#3, #25, #31, #5) plus one late relative, #13's
`adversarial-test-gap`. No change to the fix; the evidence base is now three builds.

## P30 (trust guard) · The trust guard walks the wrong ancestry for a lane worktree

*Implemented 2026-08-03. Note the ID collision: a different proposal, same-class
rejection detection, was also filed as P30 that day. Every `P30` in the scripts
refers to this one.*

The P16 guard was right in intent and blind in exactly the case this skill always
creates. `_nearest_trust` walked **filesystem** ancestors of a lane's cwd, but
SKILL.md step 4 mandates worktrees be **siblings** of the repo — so a lane cwd of
`…/Projects/<repo>-wt-5` has parent `…/Projects` and the walk reached a trusted
ancestor without ever passing through the repo root. Claude Code, running inside
that worktree, resolves trust through the **git repo** and reads the repo root's
entry instead.

**Evidence (seat-reservations build-1).** `…/Projects: true` and
`…/Projects/seat-reservations: false`. All **46 lane spawns passed the guard**;
the allowlist was ignored in every one. Nothing surfaced until the first command
that needed it — the first merge, **77 minutes in**: `merge-5` denied at 22:04:27,
`merge-21` at 22:10:58, both tickets blocked (**47m43s** of ticket time), then
merged in under four minutes with no code change once the human accepted.

**Precondition, verified before building anything.** The whole diagnosis rested on
one unverified belief — that Claude Code resolves a worktree's trust through the
git repo, not the filesystem parent. The proposal asked for a fresh probe lane;
the build's own logs answered it more directly. `lane-impl-1.log` opens with:

    Ignoring 30 permissions.allow entries from .claude/settings.json: this
    workspace has not been trusted. … set projects["/Users/everscending/
    Projects/seat-reservations"].hasTrustDialogAccepted: true

Its cwd was `…/seat-reservations-wt-1`; the path Claude Code named is the **main
repo root**. Confirmed, at zero cost.

**What shipped.**

- `_git_main_root` — the main worktree's root, via `git worktree list --porcelain`
  (*not* `rev-parse --show-toplevel`, which in a linked worktree returns the
  worktree itself).
- `_trust_check_dir` — asks both questions: the filesystem walk for the cwd, and
  the same walk for the git repo root.
- `_nearest_trust` is now **three-valued**: 0 trusted, 2 explicitly declined, 1 no
  entry anywhere. The distinction is load-bearing, and it is what the falsification
  criterion forced (below).
- `spawn-lane` refuses the **first** lane, naming the repo root — the path the human
  must actually accept — and spawns nothing.
- `tick.sh trust-check [--notify] [dir]` — the same question as a read-only verb, so
  bootstrap need not duplicate the walk and a human can ask before a build rather
  than 77 minutes into one. It never writes the flag; only a human can grant trust.
- `bootstrap.sh` treats untrusted as an **incomplete** bootstrap: it still writes
  everything (the settings file is then ready the moment trust lands) but exits
  nonzero, so tick.sh writes no `.bootstrapped` sentinel and the existing
  retry-on-next-tick machinery picks it up for free. Never fatal — the wave still
  runs, because everything up to the first merge genuinely works untrusted.
- The warning is a deduped push (`workspace_untrusted`, sentinel `trust.state`),
  once per state change, not P3's fifteen stderr lines into a log nobody reads.

**The falsification criterion did real work.** The proposal said a tightened guard
that refuses lanes which would have worked is worse than the gap it closes — and
the first implementation was exactly that. `git worktree list` returns the
**physically resolved** path while the trust file is keyed by whatever path Claude
Code was launched with, so under any symlinked prefix (`/tmp`, `/var`, a symlinked
home) the two spellings disagree, the repo-root walk finds nothing, and every lane
in a perfectly trusted repo is refused. The test suite caught it immediately. Hence
the three-valued read: **only an explicit `false` refuses**; "no entry recorded"
means *cannot tell*, and never hardens into *declined*.

**Tests.** Nine, paired as planted violations: the sibling-worktree case refusing
and naming the repo root; a repo root with no entry still cascading from a trusted
parent; an unrecorded repo root reading as "cannot tell"; the same fixture with one
`false` added still refusing; `trust-check` never mutating the trust file; the
notify sentinel deduping; and the bootstrap trio — no sentinel, the wave still runs,
and the next tick after accepting trust completes it. Suite: 324 passed, 0 failed.

**Verified against the real machine.** Replaying build-1's exact trust state against
the live `seat-reservations-wt-5` worktree, `spawn-lane` refuses and spawns nothing;
under the real (now trusted) trust file, the same spawn succeeds — no false refusal.

## P37 · Let a re-scoped ticket retire the rejection history of its old scope

**Evidence.** build-3, 2026-08-04. #67 was rejected three times, every one class
`fifo-tiebreak-still-races`, against browser-side arrival-order pairing. A human decision then
narrowed the ticket to a bounded give-up and moved the general race to #48. #48 merged and deleted
the pairing code entirely, so the old rejections were about machinery that no longer exists. The
ticket was rewritten — new title, new body, new branch, MR !63 closed — and came back to the board
carrying `rejections.total: 3` against `rejection_cap: 3`. Its first gate rejection would have
blocked it on the spot, and `same_class_tail: 3` would have skipped even the rework round. The
implementation passed, so it did not bite this time. Nothing stops it biting next time.

**Root cause.** `rejections_of` (`scripts/tick.sh:1893`) derives the whole history by scanning
every `<!-- orch-verdict FAIL … class=… -->` trailer in a ticket's comment thread. That scan is
deliberately un-losable — the thread fetch was widened twice so a ticket could not shed its history
by passing through `blocked` — and there is no way to say "this ticket is now different work". The
cap is attached to the issue number, not to the scope.

**Fix.** A tracker-resident marker, so the constitution's no-shadow-state rule holds and a fresh
session sees the same history any wave does:

- `lane.sh rescope <iid> [--file F]` posts the comment explaining what changed and ends it with
  `<!-- orch-scope-reset <iso8601> -->`. One verb, like every other tracker write.
- `rejections_of` stops its scan at the newest reset marker: trailers older than it count toward
  neither `total` nor `same_class_tail`. Keep them visible in the thread — this retires the cap,
  it does not hide the history.
- Refuse the verb from an automated caller, exactly as P36 refuses `--release-hold`. Re-scoping is
  a human decision about what a ticket *is*; a lane that could reset its own cap has no cap.

**Tests.** A ticket with three FAIL trailers and a newer reset marker reads `total: 0`; the same
ticket with the marker older than one of the FAILs still counts that one; a lane calling `rescope`
is refused and writes nothing.

## P38 · One way for a lane to fire the next wave, not two

**Evidence.** build-3, 2026-08-04 14:19:48. The merge lane for #68 merged MR !65, closed the
ticket, and then ran `tick.sh tick` itself in the foreground — pid 26952 — instead of letting its
exit epilogue fire one. It took the tick lock and then waited on itself. The wave that noticed
logged it verbatim: *"self-invoked tick.sh tick directly … waiting for that nested wave to release
the tick lock before proceeding."* Cost was a few minutes, not correctness, but it recurs at every
merge and the loop is the one thing that must not deadlock.

**Root cause.** Two mechanisms produce the same effect. `spawn-lane` already appends the epilogue
`( "$SELF_PATH" tick --from-lane … & )` to a lane's command (`scripts/tick.sh:1143`), and
`_tick_exit` replays a pending tick on the way out (`:656`). Meanwhile SKILL.md step 5 tells the
reader *"the merge lane fires its own tick when it lands"* (`SKILL.md:350`) — an invitation a model
takes literally. It then reaches for the wrong verb: `tick` is the human contract (always runs,
ignores switch and gap), where a lane handoff is `tick --from-lane` (respects the switch, ignores
the gap). Foreground, wrong contract, wrong pacing.

**Fix.** Make the wrong call impossible rather than discouraged: `cmd_tick` refuses when
`LOOM_LANE_ID` is set, naming `--from-lane` and the epilogue in the error. Then delete the sentence
in step 5 that invites it — the epilogue already does this work, and a rule the scripts enforce
does not need restating in prose (this file's own "Keep SKILL.md small").

**Tests.** `LOOM_LANE_ID=merge-9 tick.sh tick` exits non-zero, writes no lock and starts no wave;
`tick --from-lane` from the same environment still runs.

## P39 · A viewer that cannot open a pane must say so and exit

**Evidence.** build-3, 2026-08-04, 12:46 → 12:59. `watch-panes.sh` was alive the whole time, and
opened nothing: no anchor pane, no build ticker, no lane panes. The build ran two implementation
lanes through it unseen, and the human noticed only by asking why the ticker was missing. Killing
it and relaunching from a live pane opened all three panes in four seconds.

**Root cause.** The viewer anchors every split to the pane it was launched from,
`$HERDR_PANE_ID` (`scripts/watch-panes.sh:168`, and again at `:343`). When the launching session is
gone, that pane id refers to nothing and every `herdr pane split` fails. `new_pane` swallows the
failure — `2>/dev/null`, `|| true`, empty string on error (`:151`) — and the startup check is
`if [ -n "$anchor" ]`, so an empty result reads as "skip this", not "I am broken". `ensure_ticker`
does log its own failure, but the launcher redirects the viewer's output to `/dev/null`, so nothing
reaches a human. The result is a process that looks healthy in `pgrep`, polls forever, and shows
nothing.

**Fix.** Treat a failed split off the anchor as fatal, not as a skip. On the first failure,
re-resolve the anchor against a live pane; if that also fails, print the reason and exit non-zero
so the singleton is released and the next `/loom watch` or manual tick starts a working
viewer. Separately, launch it with its output going to `$LOOM_HOME/watch-panes.log` rather than
`/dev/null` — a silent diagnostic is not a diagnostic. Depends on P40: exiting is only safe once
the pidfile is owned correctly.

**Tests.** With the pane opener stubbed to fail, the viewer exits non-zero within one poll, prints
a reason naming the dead anchor, and leaves no pidfile behind. With it succeeding, behaviour is
unchanged.

## P40 · The viewer singleton guard deletes a pidfile it does not own

**Evidence.** build-3, 2026-08-04. Found live: `watch-panes.sh` running as pid 1805 with
`$LOOM_HOME/watch-panes.pid` absent. The likely sequence is an older viewer still shutting down
when 1805 started — 1805 found no pidfile, wrote its own, and the older one's `EXIT` trap then
deleted it.

**Root cause.** `trap 'rm -f "$MAP" "$MAP.new" "$WP_PID"' EXIT` (`scripts/watch-panes.sh:118`)
removes the pidfile unconditionally, without checking it still contains this process's own pid.

**Why it matters in both directions.** With the pidfile missing, the guard at `:112` passes and the
next manual tick opens a **duplicate** viewer — two panes per lane, two tickers. With the pidfile
present but belonging to a viewer that can no longer open panes (P39), the guard does the opposite:
it reports "already running — nothing to do" and refuses to start a healthy one. The guard is
load-bearing precisely because `/loom tick` launches the viewer opportunistically on every
manual tick.

**Fix.** Remove the pidfile only when it still holds this process's own pid — read it back in the
trap and compare against `$$` before deleting. Pair with P39 so a broken viewer releases the guard
by exiting rather than holding it forever.

**Tests.** Two viewers started in sequence leave exactly one pidfile holding the surviving pid; a
viewer whose pidfile was overwritten by a newer one does not delete it on exit.

## P42 · Stop the ticker announcing a replay that is not going to happen

**Evidence.** The human, watching build-3 on 2026-08-04: *"I see the 'tick landed mid-wave —
remembered for replay' message appearing every minute. This adds more noise than its worth."* The
event log for that day:

| Event | Count | Actually replayed? |
|---|---|---|
| `tick_skipped reason=wave_gap` | 253 | no — nothing was remembered |
| `tick_skipped reason=lock_held` | 155 | yes, but many collapse into one replay |
| `tick_replayed` | 79 | — |

All 408 `tick_skipped` events render as the same sentence, and 79 replays actually happened. The
253 `wave_gap` lines are not merely noisy, they are **false**: no pending file is written on that
path and no replay follows. The `lock_held` lines are true but repeat a flag that is already set —
the pending file is a flag, not a counter, so every extra one during a wave changes nothing.

**Root cause.** `tick_skipped` is emitted for three different reasons — `loop_stopped`
(`scripts/tick.sh:717`), `wave_gap` (`:722`), `lock_held` (`:727`) — and the renderer collapses all
three into one string (`:1418`). That was harmless when the timer was a slow ~15-minute backstop:
`tick_skipped` was rare and usually meant `lock_held`. The merged-scheduler design fires every 60s
and *watches* on every firing, spending only once `min_wave_gap_minutes` has elapsed — correct, and
it makes `wave_gap` the routine outcome of nine ticks in ten. A line written for the exceptional
case now prints for the normal one.

**Fix.** Mostly deletion, all in the renderer plus one condition:

- **Do not render `wave_gap` at all.** A timer declining to spend is the absence of an event. It
  stays in `events.jsonl`, where `retro` already counts it — it just stops reaching the ticker.
- **Render `lock_held` once per wave**, when the pending flag is newly set rather than every time a
  tick bounces off the lock, and word it for what it is: a tick arrived during a wave and the wave
  will re-tick on exit.
- **Keep `loop_stopped` as its own line.** Rare, and it means something specific: the loop is off
  and this tick did nothing. (Zero occurrences in the day above, which is the point — it would have
  been worth seeing.)

Roughly 408 ticker lines become roughly 79, and every survivor is true.

**Why this is not just cosmetics.** The ticker is the human's only continuous view of the build, and
its value is entirely in signal-to-noise. A line that appears every minute and means nothing trains
the reader to skim the strip, which is where the real events — `ticket_blocked`, a gate FAIL, a
merge conclusion — also live. P19 is the same complaint about wave advisories; this is its ticker
half.

**Tests.** `render-events` on a fixture log: a `wave_gap` event produces no line; consecutive
`lock_held` events during one wave produce exactly one; `loop_stopped` produces its own distinct
line; `tick_replayed` is unchanged.

## P41 · A concluded ticket should take its viewer pane with it, however it concluded

**Evidence.** build-3, 2026-08-04. #72 was reclassified from defect to finding and closed by hand;
its three lanes were killed. Its pane stayed on screen labelled `ticket 72 — idle` for a ticket
that will never have another lane. The human spotted it and asked whether closing the ticket should
have closed the pane.

**Root cause.** Panes are recycled on purpose — a finished lane keeps its ticket stamp so the next
stage of the same ticket returns to the same pane, which is what makes implement → gate → merge
read as one continuous transcript. The exception is the "finished story" rule
(`scripts/watch-panes.sh:253-266`): a `probe-*` pane always closes when its lane ends, and a
`merge-*` pane closes only if a tracker read says the ticket actually closed — that read exists
because merge lanes sometimes exit cleanly without merging, and a blocked merge must keep its pane.
Every other lane kind skips the check entirely. So a ticket that concludes any other way — closed by
hand, killed mid-flight, closed by a human outside the loop — leaves its pane stamped forever.

**Severity: cosmetic, and worth fixing anyway.** Nothing leaks. Reuse prefers a pane stamped with
the incoming lane's own ticket but falls back to *any* idle pane, so a stale stamp is claimed by the
next lane that needs one and never starves the cap. The cost is that a pane labelled with a closed
ticket reads as work still pending, which is the exact confusion the idle stamp was introduced to
prevent (build-1 2026-08-02: an idle pane read as a stall).

**Fix.** Run the ticket-closed check for **every** lane kind, not only `merge-*`, at the moment the
pane goes idle. That is the same single tracker read, at the same moment, already paid for on the
merge path — it is not new polling, and the "a failed read keeps the pane" default stays. Keep the
`probe-*` rule as is (a probe's story ends with its lane whatever the tracker says), and keep the
merge rationale in the comment, since it explains why the read exists at all.

**Tests.** With the tracker stub reporting a closed ticket, an idle `gate-*` pane closes on the next
poll; with it reporting open, the pane idles and keeps its stamp; with the read failing, the pane is
kept. Sibling viewer items: P39, P40.

## P43 · Stop the watcher reading its own no-op events as build activity (archived 2026-08-05)

**Evidence.** build-3, overnight 2026-08-05. The board held exactly one open ticket, #32, on a
sticky human hold — nothing schedulable. The heartbeat launched a wave every 10 minutes anyway:
**44 idle waves, ~9.22 USD**, each one a real headless session that read the tracker and wrote
"no change, #32 still sticky-held, halted."

**Root cause.** `_quiet_check` used `events.jsonl`'s mtime as its "did anything happen recently"
signal, inside a 120s settle window. But the watcher writes `tick_skipped` into that same file on
every 60s firing. 60 < 120, so the check answered `active` on every tick, never reached the
`blocked == count -> halted` test below it, and the halted gate in `cmd_tick` was unreachable code.
The watcher kept itself looking busy.

**Fix.** `_last_activity_ts` returns the timestamp of the newest event that is neither
`tick_skipped` nor `notify`, and the settle window measures from that instead of file mtime.
Everything the build actually does still counts; only the watcher's own bookkeeping is excluded.

**It took two rounds, and the second is the lesson.** The first cut excluded `tick_skipped`
alone. That left `notify` — which the watcher itself emits — feeding the same signal: classify
`halted`, notify, and the notification lands in `events.jsonl`; the firing 60s later reads it as
activity and answers `active`, which deletes the once-per-state-change sentinel; the firing after
that classifies `halted` with no memory and notifies again. A 2-minute oscillation that re-pushed
the halted banner forever AND let a wave through at each gap boundary, so the spend never actually
stopped. The human spotted it in the ticker within the hour. **The rule to keep: if the watcher
emits an event kind, that kind must never be able to feed the watcher's own activity signal.**

**Why the suite missed it.** Every existing quiet test passed `LOOM_QUIET_SETTLE=0`, disabling the
window under test. The new tests leave it at its real default — one asserting a file of pure
`tick_skipped` events classifies `halted`, one asserting a real event inside the window still
reads `active` so a chained handoff's few-second gap is still protected.

## P44 · Even out the right column when a lane pane opens

The right column decays. Each new lane pane is opened by splitting the *newest* pane
downward with no ratio, so herdr halves that pane: the first lane gets half the column,
the second a quarter, the third an eighth. The panes carrying the newest lanes — the
ones the human is most likely to be reading — are the smallest on screen.

**Evidence.** Measured in a live herdr session, 2026-08-05. A right column of four
panes in a 65-row area: **24 / 21 / 10 / 10 rows**, where equal is 16. The two newest
lanes had 10 rows each to show a transcript in.

**Root cause.** One line, `watch-panes.sh:399`:

```sh
[ -n "$STACK_LAST" ] && pane=$(new_pane down "$STACK_LAST")
```

`STACK_LAST` is always the bottom-most pane, and `new_pane` passes `--ratio` only when
it is given one — which this call is not. herdr's default split is 50/50, so every lane
halves whatever is left at the bottom. Nothing here is wrong; the layout contract simply
never said anything about the sizes, only the positions.

**Fix.** A `rebalance_column` step in `watch-panes.sh`, run **once per poll and only on a
poll that actually opened a lane pane**:

1. Read `herdr pane layout --pane <the new pane>`. If `.result.layout.zoomed` is true,
   do nothing — a zoomed pane is a human reading one lane, and resizing under it is noise.
2. Take the column as the panes whose `rect.x` and `rect.width` match the new pane's **and
   whose pane id is in `MAP`**. That second condition is the safety rule: the viewer resizes
   only panes it opened itself. The session pane, the ticker, and anything a human put on
   screen are untouchable by construction, not by remembering to exclude them.
3. Sort by `rect.y`. Fewer than three panes: stop. A two-pane column is already 50/50.
4. For `k` in `0 … N-2`: re-read the layout, let `R` be the summed height of panes `k … N-1`,
   and issue

   ```sh
   herdr pane resize --pane <pane k> --direction down --amount <1/(N-k) - h_k/R>
   ```

Two facts this depends on, both verified against herdr 2026-08. `--amount` is a **signed
delta on the ratio** of the nearest ancestor split on that axis, and the ratio is the top
child's share: a split at `0.32258` resized `--direction up --amount 0.1` became `0.22258`.
And in a column built by repeatedly splitting the bottom pane downward, pane `k` is the top
child of split `k`, so targeting pane `k` moves exactly the divider below it and nothing else.

Re-reading the layout between steps rather than solving the whole column in closed form is
deliberate: rows are integers, herdr quantises each ratio to whole rows, and a closed-form
pass accumulates that rounding all the way down the column. The cost is `N-1` extra reads on
a poll that has already paid for a split.

**What this must not touch.** The left column is out of scope entirely — the ticker's 25%
strip under the session pane is a separate contract (`new_pane down "$ANCHOR" 0.75`) and
keeps its size. The split-order invariant in the layout contract is unchanged. And this
fires on pane-opening polls only, never every poll: a human who drags a divider to read one
lane's output keeps that size until the next lane arrives.

**Limits, recorded rather than fixed.** Equal lands within ±1 row when the column height
does not divide by `N`. Equal is also not the same as usable — six panes in a 65-row window
are ~10 rows each whether or not they are even, and that is `MAX_PANES`' problem; do not add
a minimum-height rule here. Everything fails soft: a `pane layout` that errors, a rect that
will not parse, or a resize that fails skips the rebalance for that poll and never touches
the pane-opening path. This viewer's first rule is that deleting herdr leaves the build
unaffected (`watch-panes.sh`, header) — a cosmetic pass must not be the thing that breaks it.

**Tests** (`scripts/tick-test.sh`, against the herdr stub, which gains a `pane layout` case
reporting rects for the panes it has handed out):

- a third lane pane opens → one `pane resize` per column pane above the last, in top-down order;
- the same run with the rebalance call removed → zero `pane resize` calls;
- no `pane resize` ever names the session anchor or the ticker pane;
- a poll that opens no new pane issues no `pane resize`;
- `pane layout` exiting non-zero → the lane pane still opens, zero resizes, viewer alive;
- `zoomed: true` → zero resizes;
- a two-pane column → zero resizes.

**What would falsify it.** A build where the human reports panes resizing under them while
they were reading one — that means the pane-opening-only trigger is not the right rule — or
any `pane resize` call landing on a pane that is not in `MAP`.

## P52 · A lane that runs away is stopped, not finished

**Problem.** Nothing in the machine bounds what one ticket may spend. `impl-43` ran 456
turns at an average 426k context per turn — past the context window, so compaction had
fired and the session was re-reading its own summarised history — for 194M cache-read
tokens, about $300, or 9% of the whole build, on one ticket. The staleness watcher does not
see this: the lane is making progress the entire time, so it reads `running` and healthy.
`rejection_cap` and `crash_cap` bound *failures*; nothing bounds *effort*.

**Fix.** The watcher already stamps `<id>.progress` from the filtered event count, so the
turn count is in hand.

- `lane_turn_cap` (config, default 150) joins the other caps: layered `cfg`, surfaced with
  its source in `resolve-config`'s `.scalars`, and published in `snapshot`'s `.config`.
- `cmd_lane_status` gains a trailing `turns` column (existing columns are untouched — `rc`
  stays at `$5`) read straight from `$LANES_DIR/<id>.progress`, `-` before any stamp exists.
  `snapshot.jq` carries it through to `.lanes[].turns`, so the wave never needs a second
  tracker or filesystem read to compare a lane against the cap.
- SKILL.md step 2 (Harvest lanes) tells the wave: a `running` lane past `lane_turn_cap` is
  effort, not progress — treat it the way a spent `rejection_cap` is treated, `kill-lane`
  then `lane.sh transition <iid> blocked` with a report naming the turn count and what the
  lane was last doing. A ticket that needs that many turns was written too big (P53) or the
  lane is lost; either way the next step is a human decision, not more turns.

The comparison and the kill stay the wave's call, exactly like `rejection_cap` and
`crash_cap` — `lane.sh` already documents that blocking on a cap is a decision, made via
`transition`, not something a script enforces unilaterally.

**Tests** (`scripts/tick-test.sh`): `lane_turn_cap` defaults to 150 and is surfaced with its
layer in `resolve-config`, like the other caps; it is published in `snapshot`'s `.config`;
`lane-status`'s new `turns` column reads the `.progress` stamp and leaves `rc` in place at
column 5; a lane's `turns` travels into `snapshot`'s `.lanes[]`.

## P51 · The wave reads a brief snapshot, not the whole board

**Problem.** `snapshot` is the largest single input any wave reads, and it grows with the
build rather than with the work. On ai-workout-generator-copilot it is 73k characters, of
which 43k is 54 per-ticket rows; a wave acts on perhaps five of them. Every other row
carries `unblocked: false` or `gate.eligible: false` with no lane and no rejections — the
wave reads it, pays for it in cache creation, and pays for it again on every subsequent
turn of that session.

**Fix.** `snapshot --brief` (`cmd_snapshot`, `tick.sh`): a full row only for a ticket the
wave can act on this turn, everything else a bare iid.

- `snapshot.jq` gains `is_actionable($t; $working)` and a `$working` binding (the ticket iid,
  as a string, behind every ALIVE lane of any kind — factored out of `summary.stranded`,
  which used to compute the same set inline, so the brief filter and `stranded` can never
  read it differently). The five clauses are the five states named below.
- The final document's `tickets` key is the actionable subset under `--brief`, unchanged
  otherwise; a new `other_iids` key carries the bare iids of the rest (`[]` when not brief).
  `summary`, `epics` and `warnings` still run over the full internal ticket list either way —
  only the two output keys are filtered.
- `cmd_snapshot` takes `--brief` as its first argument and passes `--argjson brief
  true|false` into the jq program. SKILL.md step 1 names `snapshot --brief` as the wave's
  default read; plain `snapshot` (unchanged) stays for `watch`, `graph` and a human.

**"Actionable"** — a full row survives for a ticket that is any of:

1. `ready-for-agent`, unclaimed, and `unblocked: true` — the fill step's ready set.
2. `review` with `gate.eligible: true` — the gate step.
3. `merge-queue` — the merge step, including tickets behind the one being merged, because
   the queue is ordered oldest-first and the wave must see the order.
4. Listed in `summary.stranded` — `in-progress` with no alive lane, the rework path.
5. Holding a live lane of any kind, whatever its label — harvest reads these, and this is
   what still surfaces a `review` ticket already behind a running gate lane, where
   `gate.eligible` reads false precisely because it is already gated.

**Tests** (`scripts/tick-test.sh`): one fixture ticket per clause above (seven total,
including two `merge-queue` tickets to prove the whole queue survives, not just the head,
and a `review` ticket held by a live `gate-*` lane to prove clause 5 catches what clause 2
cannot) asserts `--brief` keeps exactly those six full rows; a seventh ticket — blocked by
an open ticket, unclaimed, laneless — asserts the inverse: present only in `other_iids`.
A last case asserts plain `snapshot` (no flag) still carries every ticket and `other_iids`
stays empty, so the filter is opt-in.

## P55 · `retro` reports spend, not just time

**Problem.** `tick.sh retro` explains where a build's *time* went and says nothing about
where its *money* went. Producing the table at the top of this file took a one-off script
over `message.usage` in the lane logs — data that is already on disk, already per-lane,
already attributable to a ticket by filename. Without it, every spend question is a fresh
investigation, and the expensive ticket is only discovered after the build is over.

**Fix.** `USAGE_JQ` (`tick.sh`), a jq program that reads one session's raw `.jsonl`
transcript, sums each assistant message's `usage` fields, and prices them by that
message's own `.model` against a hardcoded per-family table (`$/MTok`, dated at the
comment — the proposal's caveat, kept live rather than fixed once). `_lane_cost <file>`
wraps it for a single lane log; `_spend_by_lane` globs every `lane-*.jsonl` this repo has
ever kept (`clear-lane` never removes them) into `[{id, cost}, ...]`.

Surfaced two ways, per the fix direction:

- `lane-status` gains a trailing `cost` column (existing columns untouched — `turns` stays
  at column 6), read the same way `turns` is: computed fresh each call, no new bookkeeping.
- `retro` gains a **Spend** section: total, split by lane kind (most expensive first), the
  top five spending lanes, and a per-ticket rollup — joined by lane id against `$lanes`
  (the `lane_exit` events already scoped to the build), so a lane log from a different
  build never enters the total.

Deliberately narrower than P29 (full OTel export to LangFuse) — the local, zero-dependency
subset, meant to ship first and retire the need for P29 if it answers the question.

**Tests** (`scripts/tick-test.sh`): round token counts (1M input tokens per lane) keep the
dollar amounts on exact integers so the assertions do not chase float formatting —
`lane-status`'s `cost` column prices a fixture session log correctly; `retro`'s Spend
section reports the right total, the right per-kind split in cost order, names the top
spender, and rolls the right amount up to the ticket its lanes worked.

## P53 · Ticket size is a phase-4 output, like width

**Problem.** Implementation lanes are 57% of build spend, and a lane's cost is decided when
its ticket is written, not when it runs. Phase 4 already treats *width* — how many tickets
can start at once — as a deliberate ticket-writing output with a measured verdict in phase
5. It treats *depth* as nobody's business. The result is a long tail: median impl lanes
finish in well under 100 turns while the top five run 280–456, and those five alone are
roughly a quarter of the implementation bill.

**Fix.** Two halves, exactly as proposed. *Ticket side* (`references/ticket-template.md`):
a new `## Size` section, alongside `PRD requirement`, stating the rule in prose — a ticket
whose acceptance criteria cannot plausibly be met in one focused sitting is split, using
`Pinned interfaces` as the same splitting tool width already uses — and naming the `graph`
verdict that makes it checkable. *Measurable side*: `snapshot.jq` computes two cheap proxies
per ticket while it already has the description in hand — `criteria_count` (checklist items
under the ticket's own `## Acceptance criteria` section) and `file_surface` (distinct
file-extension tokens anywhere in the body, extension-whitelisted to keep prose like "e.g."
from inflating it). `tick.sh graph`'s `GRAPH_JQ` reads both off `.tickets[]`, flags any
ticket over threshold (`criteria_count > 6` or `file_surface > 6` — a starting point, not a
calibrated cutoff; both fields default to 0 so a pre-P53 snapshot or a fixture that never
sets them reads as not-deep, never null-propagates into a false positive) into a structured
`likely_deep` array, and folds a `LIKELY DEEP — #<iid>...` clause onto `.verdict` alongside
`CHAIN-SHAPED`/`NARROW START`. `references/phases-1-5.md` phase 5 names the new verdict in
the same sentence as the other two, pointing back at the ticket-template size rule.

**Deviation from the Fix section as written.** The proposal placed the size rule "alongside
the existing width rule" in `references/ticket-template.md`; the width rule itself actually
lives in `references/phases-1-5.md`'s phase 4 section, not in `ticket-template.md` (which has
no width rule to sit beside). Implemented as literally directed — the size rule went into
`ticket-template.md` as named — and cross-linked phase 5's verdict-reporting sentence to it
instead, since that is where the width verdict's own instruction actually sits.

**Pairs with P52** (`lane_turn_cap`, archived above): P53 stops writing the runaway ticket,
P52 stops paying for one that got written anyway.

**Tests** (`scripts/tick-test.sh`, section 7g): an outsized `criteria_count` alone is flagged
`LIKELY DEEP` in both `.likely_deep` and `.verdict`; an outsized `file_surface` alone is
flagged too; a ticket comfortably under both thresholds raises nothing (the planted-violation
discipline already used for `CHAIN-SHAPED`); a ticket carrying neither field at all reads as
not-deep rather than erroring. `snapshot.jq`'s extraction itself was hand-verified against a
synthetic ticket body (4 checklist items under `## Acceptance criteria`, 3 distinct file
tokens across an unrelated section) but has no test of its own in `tick-test.sh`, which
exercises `graph` directly against synthetic snapshot JSON rather than through `glab`.

## P57 · Acceptance criteria travel with the probe, not with every wave

**Problem.** P51 shipped and worked — the snapshot on ai-workout-generator-copilot went from 76,360
to 16,832 characters, a 78% cut, with the correctness guard passing (four actionable tickets kept as
full rows, fifty as bare iids, fifty-four accounted for). That success moved the bottleneck rather
than removing it. The `epics` block was never touched, so it is now **10,470 of the remaining 16,832
characters — 62% of everything a wave reads** — against 3,107 characters of ticket rows.

Inside that block the split is lopsided in exactly one direction. Across ten epics, every structural
field together — `name`, `milestone`, `source`, `complete`, `accepted`, `needs_probe`,
`open_tickets` — comes to about 1,070 characters. `acceptance` alone is **8,222**, or 88%.

And a wave reads that text in exactly one place: step 6, when assembling a probe brief for an epic
in `summary.epics_awaiting_probe`. Every other wave pays for it and uses none of it. On this repo
`epics_awaiting_probe` is empty and all ten epics have `needs_probe: false`, so all 8,222 characters
are dead weight on every wave that runs — carried into context at cache-creation price, then re-read
on every turn of a session averaging 28 turns.

The asymmetry is what makes this worth doing rather than tolerating: probes were 22 sessions in the
measured build, waves were 407. The criteria are needed by the rare session and paid for by the
common one.

**Fix.** P51's own rule, applied one level up, in `snapshot.jq` alone. In `--brief` output, an epic
carries its full entry — `acceptance` included — when `needs_probe` is true (the same selector
`epics_awaiting_probe` already uses); otherwise `del(.acceptance)` drops the key and keeps every
structural field. The `epics` block used to assemble the output document unconditionally
(`epics: $epics`); the trim is applied only there, as a projection over the already-finished `$epics`
value, so the warnings computed earlier in the same program (including the "ready to probe but no
criteria section" one) still read the untrimmed criteria and cannot be fooled by the cut. Plain
`snapshot` (no `--brief`) is untouched. No SKILL.md change: the rule is enforced by the filter, not
decided by a wave.

**Tests** (`scripts/tick-test.sh`, alongside the existing acceptance-rollup fixture): with both
"Ledger core" (open tickets, `needs_probe: false`) and "Reporting surface" (`needs_probe: true`)
carrying their own `## Acceptance criteria` section, `--brief` output keeps "Reporting surface"'s
`acceptance` byte-identical to plain `snapshot`, drops the key entirely from "Ledger core" (asserted
with `has("acceptance")`, not merely `== null`, so a filter that keeps the key and blanks it still
fails), and confirms "Ledger core" keeps its structural fields (`needs_probe`, `open_tickets`) under
the same trim. Full suite: 456 passed, 0 failed.

**Relation to P54.** These two now overlap: with the epics block cut, the second snapshot read P54
targets falls to roughly 2k tokens, and P54's own estimate — already reduced from 4-6% to about 1%
by P51 — shrinks further. Re-measure against a post-P57 `retro` before spending anything on P54.

## P58 · Phase 4 drafts the whole set, then checks its own output once

**Problem.** Phase 4 routes to `/to-tickets`, whose step 5 publishes one issue per ticket in
dependency order. Each body is composed, pushed, and left behind before the next one starts, so
**nothing ever holds the set**. Consistency across tickets is whatever survives in one long context,
and it degrades as the set grows. `/to-tickets` step 4 then reviews the *breakdown* — title, blocking
edges, one line of what each ticket delivers — never the bodies, so the human approves a shape and
nobody reads the acceptance criteria as a body of work.

**Evidence.** A single read of all 54 tickets of ai-workout-generator-copilot build-1, before start
on 2026-08-06, found **nine ambiguities, every one of them in the join between two tickets and
invisible from inside either**. Four would have failed the build or the demo: three tickets promised
a Graph tab the build excluded; #34's acceptance forbade the retry its own design section required,
with a test enforcing the contradiction; #36's intent list omitted the intent #54 exists to handle;
#50 required progress states from an endpoint with no channel to deliver them. The other five were a
rework round each. None was reachable by reviewing one ticket, and the blocking-edge closure check at
build definition could not see any of them — it reads links, and these were written in prose.

The set is ~95KB, about 25k tokens. It fits in one context comfortably; the pass that found all nine
took one read.

**Fix direction.** Publishing moves to the end of the phase, and an artifact the phase currently has
no concept of is added in front of it:

1. Read the source documents — unchanged.
2. Write every ticket body into **one draft file, one epic at a time**. Per-epic because a single
   pass over 58 bodies drifts by the end: the last epic's vocabulary wanders from the first's.
3. Re-read the whole draft **from the file**, not from memory. This step does not exist today and is
   the only one that can see across tickets.
4. Run **one** check list over the draft — the phase's single self-check, replacing three rules
   that today sit in three different files and fire at three different times (see below):

   *Shape* — is this set buildable at speed?
   - **width**: how many tickets can start at once, and at every layer, computed from the draft's own
     edges. Where a heavy blocker gates several dependents, split it with a `Pinned interfaces`
     ticket.
   - **size**: no ticket whose acceptance criteria cannot plausibly be met in one focused sitting
     (P53's `criteria_count` and `file_surface` proxies, read off the draft instead of the tracker).

   *Consistency* — does the set agree with itself?
   - every pinned interface names its fields (P59);
   - every field a later ticket reads exists in the ticket that pins it;
   - every capability one ticket's criteria assume has a ticket that builds it;
   - shared vocabularies — status and severity words, intent lists, state names — are identical
     everywhere they appear;
   - no ticket's acceptance criteria contradict its own mandatory adversarial tests;
   - every command a ticket's gate tier will run exists by the time that ticket merges.
5. Show the human **the bodies**, not the titles, with the surviving ambiguities as decisions to
   answer. `/lavish` already carries this shape.
6. Apply the answers to the draft file.
7. Hand the finished set to `/to-tickets` to publish. It keeps owning slicing, blocking edges and the
   tracker mechanics; it stops owning the order in which bodies are decided.
8. Keep the draft file. `replan` diffs against it.

**Folding in the rules that already exist.** Phase 4 has accumulated three separate "check your own
output" rules, written at three different times and living in three places:

| Rule | Today | Fires |
|------|-------|-------|
| Width | `phases-1-5.md` phase 4 prose: "width is a ticket-writing output, not an afterthought" | decided in phase 4, **measured in phase 5** once the Build issue exists |
| Size | `ticket-template.md` `## Size`, plus `graph`'s `LIKELY DEEP` verdict (P53) | measured in phase 5, from the tracker |
| Consistency | nothing | never |

All three ask the same question — *is the set I just wrote any good?* — and two of them can only be
answered after the tickets are already published, which is why phase 5 exists partly to send you back
to phase 4. The draft file collapses that: width is computable from the draft's edges, size from its
criteria counts, consistency from reading it. **One gate, one list, before anything is published.**
Phase 5 keeps its verdict as a backstop on the published build; it stops being the first time anyone
finds out. A ninth ambiguity from the 2026-08-06 read belongs to that same list and to no existing
rule: three E0 tickets carried gate tiers naming commands their own build had not written yet, which
neither width nor size nor the edge check can see.

**Where it goes.** Loom's own layer, never `/to-tickets` — that skill is shared with other work and
this file's *stay inside this skill* rule binds. The seam already exists: phase 4 is defined as
"route to `/to-tickets` **plus** the additions in `ticket-template.md`". The draft file, the check
list and the human review are more additions; `/to-tickets` step 1 accepts conversation context, so a
finished draft set is valid input to it.

**Cost.** One extra full-set read and a fix round — roughly 40k tokens on a 58-ticket build. Against
one lane blocked at layer five on a shape the rules call non-relitigable, with three tickets queued
behind it, it is not a close call.

**What would falsify it.** A drafted-and-checked set that still ships cross-ticket contradictions at
the same rate — meaning the check list, not the missing artifact, was the constraint. Or a set small
enough (say under 15 tickets) that one context never lost the thread, where the extra pass finds
nothing and should be skipped.


**Consumer.** Phase 4, and every ticket that imports a pinned shape without renegotiating it.

## P59 · A pinned interface names fields, not references

**Problem.** `ticket-template.md` requires a **Pinned interfaces** section when tickets share a seam:
"the exact signature goes verbatim into *every* affected ticket". Nothing checks that what lands
there is a signature. A section listing an endpoint path satisfies the requirement identically to one
listing a schema, so a ticket can promise non-relitigable stability for something it never wrote
down — and a reviewer checking "is this pinned?" gets a yes.

**Evidence.** Two of build-1's three interface tickets did it, and the same cause produced both:
phase 4 transcribes what the documents of record name, and neither shape was named anywhere.

- **#5** pinned "request and response schemas for `/api/members`, `/api/plan`, `/api/copilot`,
  `/api/graph/focus`" — endpoint paths, no fields, no type names. Meanwhile #42 renders six specific
  member fields, #40 a churn indicator, #43 a five-field snapshot with churn reasons carrying their
  numbers. Whoever implemented #5 would have invented the member shape, and it would have been
  non-relitigable from that moment — with #42 arriving at layer five to find its field missing.
- **#9** is data-only, starts on day one, and #12 and #13 are specified to fail loudly against its
  file. It carried no Pinned interfaces section at all, so three tickets would have started in
  parallel against a format one of them was still inventing.

Both were fixed by hand on 2026-08-06, before start. Neither was caught by anything.

**Fix.** One line in `ticket-template.md`, and one in the phase-4 rules: a **Pinned
interfaces** section states the fields, values and shapes — a type body, a JSON example with its
field rules, a function signature. An endpoint path, a bare type name or a file path is a reference,
not a pin. And: **an interface ticket whose shape appears in no document of record must specify the
shape itself** — that is precisely the case where there is nothing to transcribe, and precisely where
both failures happened.

This is a checkable rule; the P58 step-4 checklist should pick it up too once P58 ships. It is also
independently useful: on its own it would have caught both #5 and #9 without any of P51's machinery.

**Tests.** Prose-only change in `references/`, which this skill's test suite does not cover — no
`tick-test.sh` addition applies. Correctness here is a reading, not a check.

## P47 · Guards fail closed

**Problem.** Every guard read in `lane.sh` was `… 2>/dev/null … || true` (`:136`, `:221`, `:466`,
`:529`), so an API failure made the guard *pass*. Demonstrated: with the `closed_by` read failing,
`lane.sh close 70` closed the ticket having checked no MR; with the issue read failing, a lane
transitioned a ticket carrying a human `blocked` hold. `cmd_sweep`'s merge check had the same
shape — `git log "origin/$base..$branch" 2>/dev/null` could not tell "no commits ahead" from
"range does not resolve", so an unfetched or missing base ref armed the delete path on a worktree
holding real work.

**Fix direction.** Separate "read succeeded and says no" from "read failed": capture the exit
status, and on failure `die` with the reason.

**As implemented (2026-08-06).** Each of the four `lane.sh` reads now runs as its own statement —
`out=$("$GLAB" api … 2>/dev/null) && rc=0 || rc=$?` — so the API call's exit status is captured
independently of whatever jq does with its output; `set -euo pipefail` would otherwise abort the
script on the bare assignment before a message could be composed, which is why the `&&`/`||` pair
is load-bearing and not just style. A non-zero `rc` dies naming the read that failed and why the
guard cannot proceed blind, instead of falling through to "not blocked" (`_blocked_guard`), "not
closed" (`cmd_transition`), or "no open/merged MR" (`cmd_close`, `cmd_merge_failed`). `cmd_sweep`'s
`git log origin/$base..$branch` gets the same treatment in `tick.sh`: its own exit status is
captured before the emptiness check, and an unresolvable range now skips the worktree with a
logged reason rather than reading as "no commits ahead, safe to delete". `cmd_merge`'s existing
`closed_by` read was left alone — it already fails closed (empty `mr` → `die`), just with a
misleading message on an API error; not the shape this proposal was about.

**Tests.** Five new cases in `scripts/tick-test.sh` §23, each failing exactly the one read the
guard depends on and asserting both a `die` and that nothing was written: `_blocked_guard` (via
`close`, whose issue-state read precedes its own), `cmd_transition`'s closed-ticket read,
`cmd_close`'s `closed_by` read (isolated from `_blocked_guard` by leaving the issue-state read
healthy), `cmd_merge_failed`'s `closed_by` read, and `cmd_sweep`'s unresolvable base ref. Full
suite: 461 passed, 0 failed (456 → 461).

## P46 · `stale` means alive — one liveness reader, not four

**Problem.** `lane-status` reports `running | stale | dead`, where `stale` is "pid alive, no model
turn for `heartbeat_stale_minutes`" — the wedge state a human triages. Four consumers filtered on
`running` alone and so treated a live lane as gone: `cmd_sweep` (`tick.sh:164`), whose live-cwd set
is the only thing standing between a live lane and `rm -rf` of its worktree; `_quiet_check`
(`tick.sh:313`), which then classified `halted` or `complete` with a lane still holding a ticket;
and `watch-panes.sh:408`, which closed a stale probe's pane and marked a stale implementer's pane
idle and reusable.

**Fix direction.** One helper — `_lanes_alive` — returning `running` **and** `stale`, used
everywhere the question is "is a process there"; `running` stays only where the question is "is it
making progress".

**As implemented (2026-08-06).** `tick.sh` gains `_lanes_alive()`, a one-line wrapper around
`cmd_lane_status | awk '$3=="running"||$3=="stale"'`, placed next to `cmd_lane_status` itself.
`cmd_sweep`'s live-cwd loop and `_quiet_check`'s early-active check both call it in-process instead
of hand-filtering on `running`. `watch-panes.sh` runs as a separate process and can only reach
`tick.sh` through its CLI, so `_lanes_alive` is also exposed as a `lanes-alive` subcommand;
`watch-panes.sh`'s poll loop now reads `tick.sh lanes-alive` instead of piping `lane-status` through
its own `awk '$3=="running"'`. `snapshot.jq`'s gate-eligibility read was already correct (`state !=
"dead"`, P11) and needed no change — it was the "lesson already written down" the proposal's
Evidence pointed at, not a fourth site to fix.

**Tests.** Three new cases in `scripts/tick-test.sh`, one per consumer, each spawning a real
background lane and forcing it `stale` (`heartbeat_stale_minutes: 0` plus a backdated log) rather
than asserting on a mock: `sweep` keeps a merged-branch worktree alive under a stale lane instead of
deleting it; `_quiet_check` (via the `WATCH`/`tick --auto` path) reads `active` and returns before
ever calling `glab`, proven by a stub that plants a marker on any call and asserting the marker
never appears; `watch-panes.sh`'s poll keeps a stale lane's pane live — no idle rename, no close.
All three fail against the pre-fix code (confirmed by running them against the unmodified scripts)
and pass against the fix. Full suite: 468 passed, 0 failed (465 → 468, three new cases).

## P48 · The wave prompt is generated, not hand-maintained

**Problem.** `tick.sh:885-891` composes the context injected into every wave, prefaced "trust it
over rediscovery" — so where it contradicts `SKILL.md`, it wins, from inside the session. It
tells every wave to spawn lanes with a flat `--model <lane_model>`, defeating P31's per-ticket
escalation so a rework round runs on the tier that just failed; it lists the `lane.sh` verbs
without `merge`, `merge-failed`, `fix-ticket`, `reconcile` or `probe-result`; and it instructs
merge lanes to finish with `lane.sh close`, the build-1 merge-1 failure `cmd_merge` was written to
end and `cmd_close` now hard-refuses.

**Fix direction.** The prompt states only facts tick.sh *owns* — repo root, state dir, script
paths, permission mode, the first action — and derives the rest instead of restating it: the verb
roster from `lane.sh`'s own usage output, the per-ticket model from the snapshot's `.model`, and
nothing at all about which verb finishes a merge (that is a decision, and it lives in SKILL.md).
A suite case asserts the injected verb list equals `lane.sh`'s usage list, so the two cannot drift
again.

**More evidence (ai-workout build-1, 2026-08-07).** The same hand-maintained-prose failure shape
reached lane briefs: a wave's brief told impl-2 to invoke `/implement` as a slash command —
impossible in a headless session — costing two dead spawns before a later wave rewrote the brief
inline. P68 (adopted 2026-08-07) is the brief-side companion to this proposal.

**As implemented.** `_lane_verbs <lane.sh>` runs `lane.sh` bare, keeps the text after
`usage: lane.sh `, and splits it on `" | "` — the spaced separator, so the alternatives written
*inside* one segment (`pass|fail`, `--url <url> | -- <cmd...>`) cannot masquerade as verbs — then
takes each segment's first token and drops anything that is not a bare lowercase word. The result
is interpolated into the prompt where the hand-written list used to sit; if `lane.sh` is
unreadable the clause simply collapses to "run it bare for usage" rather than inventing a roster.
The spawn line now carries `--permission-mode <mode>` alone and sends the wave to the ticket's
`.model.effective` for the model, so `cfg lane_model` no longer reaches the prompt at all (it is
still read by `snapshot` and `resolve-config`, which is where the escalation chain belongs). The
`lane.sh close` sentence is deleted outright, not reworded. The brief bullet gained one clause
each for P68's two new behaviours, since a wave composing a brief has to know about them.

**Tests.** `scripts/tick-test.sh`: the injected roster equals `lane.sh`'s own dispatch table
compared as a set (usage order and dispatch order differ and neither is a contract); a configured
`lane_model: sonnet` never reaches the prompt as a flat flag and `.model.effective` does; the
prompt names no merge-finishing verb; and — the failing side — a doctored `lane.sh` beside a copy
of `tick.sh` puts a verb this suite has never heard of into the prompt verbatim, which a
restatement could not do. Full suite: 545 passed, 0 failed (536 → 545, shared with P68).

## P49 · Every tracker read paginates

**Problem.** `_epics_unaccepted` (`tick.sh:246-247`), `_quiet_check` (`:306`) and the snapshot's
`closed.json` (`:1889`) read `per_page=100` with no `--paginate`, unlike `:1775` and `:1798`. Past
100 closed members, an epic whose tickets all closed early contributes no milestone title, the
acceptance gate returns false, `_quiet_check` prints `complete`, and the completion wave tears the
agent down with that epic never probed — the build-2 failure the gate exists to prevent, reachable
again by size alone. The open-issue read truncates the same way, so `blocked == count` is compared
over a truncated set.

**Fix direction.** One helper that every tracker read goes through, paginating by default; a
suite fixture that exceeds one page (none does today) for the acceptance gate, the quiescence
count and the snapshot.

**Implementation (2026-08-07).** Entirely in `scripts/tick.sh`. `_glab_list [--capped] <path>`
runs `$GLAB_CMD api --paginate <path>` and folds the one-array-per-page output into a single
array, returning non-zero when the call failed *or* the result was not an array — so every
caller's existing failure path still fires unchanged. All nine tracker reads in the script go

## P63 · Finishing is one verb, and the snapshot spots the half-finished

**Problem.** A lane finishes with several tracker writes in sequence — push, open MR, move label;
or post verdict, move label. A session death between steps strands a finished ticket in a state
no scheduler step looks at, and recovery is model judgment in a later wave.

**Evidence (ai-workout build-1).** Four incidents: #31 pushed MR !8 then died before the relabel

deterministically flags the two stranded shapes — open MR with `Closes #n` but ticket not in

**Implemented 2026-08-07.** `lane.sh submit <iid> [--title <t>] [--file F]` is the last write of

## P66 · Reconcile re-installs every ecosystem the merge touched

**Problem.** `lane.sh reconcile`'s dependency sync looks only at the root Python manifest
(`uv sync`); a merge that moves a nested lockfile (`web/pnpm-lock.yaml`) leaves that ecosystem
uninstalled, and the post-reconcile gate dies on a missing tool.

**Evidence (ai-workout build-1).** merge-10 failed twice (03:30) on `openapi-typescript` missing
from `web/node_modules`; #10 was still unmerged when the build stopped and will fail the same way
on resume.

**Fix.** The sync step detects every lockfile the merge moved — root or nested — and runs the
matching installer per ecosystem. Suite case: a merge staged to move only a nested lockfile
asserts the nested install ran.

**Implementation (2026-08-07).** Entirely in `scripts/lane.sh`; `SKILL.md` unchanged (net 0 lines
— step 5 already says reconcile re-installs when the merge moved a manifest or lockfile, and that
sentence is still true). `_sync_deps` no longer resolves ONE command against the working
directory. It keeps the same cheap precondition — the merge must have moved a manifest or a
lockfile at all — then walks every changed path, resolves an install directory and command per
path through the new `_install_cmd_for`, dedupes on `dir+command`, and runs each one with `cd`
into its own directory. So a merge moving `web/pnpm-lock.yaml` installs in `web/`, and a merge
moving both root and nested lockfiles installs twice.

`_install_cmd_for <dir>` prints `"<install dir>\t<command>"`, or nothing. It keeps the old
lockfile-before-manifest precedence, but searches the directory and then its ancestors for a
LOCKFILE first, and only falls back to a manifest in the directory that actually moved. That
walk-up is what makes a monorepo work: `apps/api/package.json` moving in a pnpm workspace
installs at the root where `pnpm-lock.yaml` lives, instead of guessing `npm install` inside the
package and writing a second, wrong `node_modules`. It returns 0 explicitly — under `set -e` a
falling-through `elif` chain would otherwise take the whole reconcile down. `LANE_INSTALL_CMD`
and `LANE_SYNC_DEPS` keep their meanings; the override now applies per ecosystem.

Three new suite cases beside the existing three: a merge moving only a nested lockfile writes its
(relative-path) install marker in `web/` and NOT at the root — the discriminator, since the old
code's regex matched the nested path and then installed at the root; a merge moving two
ecosystems installs both; a lockfile-less workspace member installs at the workspace root. Full
suite: 487 passed, 0 failed (484 → 487).

One note on the evidence. It still reproduces as written — merge-10's logs say
`openapi-typescript` missing, `web/node_modules` never installed — but they carry no
"moved a manifest or lockfile" line, so on that ticket the nested ecosystem was never installed

## P67 · One gate per commit

**Problem.** The impl→gate chain handoff and the scheduler's gate step can both spawn a gate for
the same ticket at the same HEAD. P11 deduplicates *sequential* re-gates via the verdict trailer;
nothing covers the *concurrent* case, so two full review sessions run and the last verdict write
wins.

**Evidence (ai-workout build-1).** gate-14 and gate-14-r2 live simultaneously on one HEAD (wave
note 03:49); #41 rounds 2 and 3 both PASSed the same SHA; #8 gated twice within a minute
(06:00, 06:01). Pure duplicate spend.

**Fix, as implemented.** `spawn-lane` refuses a gate lane when a live gate lane already holds the
same ticket and HEAD — the merge-lock shape (mkdir-atomic, PID-owned, stale-broken), applied per
ticket+commit instead of one shared dir, so gates on unrelated tickets or unrelated commits never
queue behind each other. `_gate_lock_reserve`/`_gate_lock_owner` are the merge lock's two
functions verbatim, parameterized by a `<ticket>@<sha>` key under `$LOOM_HOME/gate.lock.d/`.
`cmd_spawn_lane` reads the ticket off the lane id (`gate-<ticket>[-r<round>]`, stripping the round
suffix) and the commit off `git -C <worktree> rev-parse HEAD` — the worktree's actual HEAD, never
trusted from the id, so a stale round number can't fool it. The lock is reserved before any
destructive step (same place the merge lock reserves), released in the lane's own exit epilogue,
and restamped with the lane's own pid from inside the lane for the same reason the merge lock
does: the reserving process (`spawn-lane` itself) exits almost immediately, so leaving its pid on
the lock would make it look abandoned within moments. A worktree with no determinable HEAD (not a
git checkout yet, or no commits) has nothing safe to key on, so the guard steps aside entirely —
this is the only reason a gate spawn there is unaffected. Chain and scheduler race safely; the
loser's `spawn-lane` call dies in milliseconds with no lane and no pid file left behind.

**Tests.** `scripts/tick-test.sh`: a duplicate gate on the same ticket+HEAD is refused and leaves
no lane; a different ticket at the same HEAD is unaffected (proves per-ticket, not one shared
lock); the same ticket at a new HEAD is unaffected (proves per-commit, not a standing hold); a
killed gate lane's lock is broken by the next attempt; an instant gate lane spawns cleanly with no
stamp race, and the lock it releases is genuinely free for the next round; a non-git cwd has no
HEAD to key on and never blocks. Full suite: 536 passed, 0 failed (529 → 536). SKILL.md:
unchanged — the guard is transparent plumbing inside `spawn-lane`, the same class as the existing
duplicate-live-lane-id guard, which SKILL.md also never narrates.

## P56 · A probe that cannot finish fails fast

**Problem.** Probe lanes average 162 turns and 26.6M cache-read tokens each — the highest
per-session cost of any lane kind, ahead of implementers. The probe brief already mandates a
hard attempt cap on polling, where hitting the cap is a failure to report, but the cap is
prose in a generated brief rather than anything the machine enforces, and most of those
turns are the poll loop.

**Fix.** The poll loop becomes `lane.sh wait-ready --timeout <secs> [--interval <secs>]
(--url <url> | -- <cmd...>)`: one deterministic call instead of a model-driven curl+sleep
turn loop. It polls the URL (via `curl -fsS`) or runs the given command every `--interval`
seconds (default 2) until it exits 0 (ready, rc 0) or `--timeout` seconds pass (not ready,
rc 1) — never past its own deadline, so hitting it is a single rc a probe checks, not a

## P73 · A shared bash lib for the facts every script re-derives

**Problem.** The base-branch rule — config `base`, else `develop` if `origin/develop` exists,
else `main` — is written six times: tick.sh `cmd_sweep` (189), `_base_ref` (2883),
`cmd_resolve_config` (3132); lane.sh `cmd_base_check` (356), `cmd_reconcile` (593),
`cmd_submit` (800). The sixth already drifts: `submit` probes with `ls-remote` and never
consults the config key, so a repo that sets `base:` gets MRs targeted by a different rule
than the one its merges reconcile against. The lockfile→toolchain table exists twice
(`detect_stack`, tick.sh:2795; `_install_cmd_for`, lane.sh:679 — "kept as its own copy" by
its own comment); `die` three times; `_yaml_scalar`-shaped config reading twice.

lane.sh's standing rationale — "deliberately stands alone" — is about not sourcing *tick.sh*,
whose top level has side effects (mkdir, the `.orchestrator.yml` refusal, REPO_ROOT
resolution, exit paths). It is not an argument against a side-effect-free function file, and
P70 has already made that call: `glab-lib.sh` is a sourced shared file. This proposal widens
that seam rather than opening a second one.

**Fix.** One `scripts/lib.sh` (P70's `glab-lib.sh` becomes this file, or is folded into it if
P70 lands first — one sourced lib, not two). Entry rule, stated in its header: pure functions
only, nothing runs at source time, no tracker mutations ever. Contents: `_glab_list` (P70),
`_detect_base <dir>`/`_base_ref <dir>` (all six call sites migrate, `submit` included —
that is a behavior fix and the test below pins it), the lockfile→toolchain/installer table
(one table serving `detect_stack`, `_derive_gates_tsv` and `_install_cmd_for`), `_lane_type`,
`_yaml_scalar`/`cfg`/`cfg_source`, and `die` (prefix from `$0`). Resolved and sourced via the
`dirname` pattern every script already uses to find its siblings, with a loud die when
missing. The read/write charter is untouched: the lib mutates nothing, tick-test.sh's
argv-scan of mutating verbs still binds on tick.sh, and lane.sh still never sources tick.sh.

**Tests**: source-time purity — sourcing lib.sh in a bare environment creates no files and
prints nothing; per-migrated-site behavior pins — sweep/resolve-config/base-check/reconcile
against fixtures where the answer is `develop` vs `main` vs a config `base:`; and the drift
fix — `submit` in a repo with `base:` set targets that base (a case that fails against
today's code).

**Consumer.** Every future ecosystem or base-rule change (lands once instead of six times),
P70's four migrated reads, and P74's lane.sh helpers, which live beside these.
