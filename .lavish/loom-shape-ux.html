Shape
A worker × round grid, not a ticket list.

Rows are the workers you configured — four impl lanes, then the aux pool's gate, merge and probe. Columns are now, +1 and +2. An empty cell is a worker about to sit idle, the one fact no existing loom view shows.

Language
Build it in bash + jq, not Python.

graph.jq already computes a depth fixpoint over blocked_by. Python would be the repo's only Python file, beside 6,884 lines of bash tests.

The screen

Workers down the left, rounds across the top. Impl lanes and the aux pool are separate bands because they are separate pools with separate caps — an impl ticket handing off to a gate frees its impl slot immediately, and that handoff is why the next ticket starts.

There is one screen, not six. The app has two layouts for the same board, three overlays that draw on top of either, and one modifier that changes the numbers without changing the layout. The buttons below are not a menu of screens — the first row is the layouts and overlays, the second row is the same board at different moments, to show how it behaves.

Where a ticket goes after impl



This is the part revision 2 got wrong. A ticket does not finish when its implementer
finishes — it finishes when its merge request is merged and the issue closes. Between those
two moments it passes through two more workers, from a different pool:



  TICKET LABEL   in-progress ─────► review ─────────► merge-queue ─────► closed
  (tracker state)       │              │                   │                ▲
                       │         ⌛ a queue          ⌛ a queue          │
                       │         nobody is           nobody is           │
                       │         working             working             │
                       ▼              ▼                   ▼                │
  WHO IS WORKING  ● impl-12      ◆ gate-12-r1        ◈ merge-12 ────────┘
  (a lane, a pid)  writes code    runs the tier's     rebase onto base
                   opens the MR   gate commands       then merge
                                       │ ✗ FAIL
                   slot frees          └──► back to in-progress, round 2
                   HERE
                                  impl pool: max_lanes 4
                                  aux pool:  max_aux_lanes 4 — gate, merge and probe share it
                                  merge lock: ONE, globally, whatever the pool says



review vs gate — a label and a worker, not two stages



They are different kinds of thing, which is why they sit in different bands above.
review is a label on the ticket: the implementer opened a merge request and
let go. gate is a lane — a real process with a pid, named gate-12-r1, running
this tier's commands. A ticket wears the review label the whole time, before a gate
lane picks it up, while one runs, and after one finishes.



So review mostly means nobody is touching this. Three of the five labels
do:




  
Ticket labelWorker on itWhat is actually happening

  
ready-for-agentnoneQueued. May be blocked, may just be out of slots — the board's ⧗ and ▪ say which.

  
in-progress● an impl laneSomeone is writing code. The only label that always has a worker.

  
review◆ a gate lane, sometimesMR is open. Waiting to be gated, being gated, or already judged and waiting for the next wave to move it on.

  
merge-queue◈ a merge lane, sometimesGate passed. Waiting for the merge lock, or holding it.

  
blockednoneOut of the machine's hands. Needs you.






  "In review" is not the same as "gateable". A gate lane starts only when four things
  hold at once: the label is review, an open MR exists, no gate lane is already
  live on that ticket, and this exact commit has not already been judged. Miss any one and
  the ticket sits in review doing nothing — the commonest confusing state on the
  board today, because nothing tells you which of the four is missing. The grid marks it
  ⧗ judged, waiting for the wave and names the reason.




Two consequences the grid now shows directly:



    
  
  1. The impl slot frees early. A ticket in gate is not holding an impl lane, so the
  next impl ticket can start while it is still being verified. That is why the impl band and
  the aux band drift out of step, and why they need separate rows.
    2. 
  
  2. Merge is single-file. One merge lock, globally. A round that lands four tickets
  produces four sequential merges, and the last one waits for the first three. On a wide
  round that tail is the slowest thing on the board, and it is invisible today — the merge
  row makes it a number you can read.
    3. 





  So a round is one generation of tickets closing — not one lane hop, and not
  a scheduler wave. Column +1 is the board after everything currently in flight
  has gone impl → gate → merge → closed. Gate and merge traffic sits in the same column as
  the impl work that caused it, because it all happens inside that generation. This matters
  for arithmetic: a blocking edge clears when its blocker closes, so a dependent
  cannot start in the same column as its blocker no matter how fast the code lands.




Reading the board




  
●impl lane running this ticket

  
◆gate lane — running the tier's checks

  
◈merge lane — rebasing and merging

  
⧗waiting on a blocker — the edge is the reason

  
▪waiting on a worker slot — nothing blocks it, the pool is full

  
○idle — the worker has nothing it is allowed to do

  
⚠blocked label — needs a human, sits outside the grid

  
══on the critical path — the chain that sets the round count





Three states of not-working, kept apart on purpose. ⧗ means
the graph is narrow — more lanes buy nothing. ▪ means the graph is wide
and you under-configured the pool. ○ means the worker is simply spare.
Today all three look identical from /loom watch: quiet.



Three rounds is the honest limit. Round 4 assumes three consecutive generations with
nothing going wrong, and a gate rejection sends a ticket back a round roughly one time in
four in this repo. A number the board cannot stand behind should not be on the board.



Everything past the window is a count, never a list. The beyond +2 line is one
line whether three tickets remain or ninety — that is what keeps the board readable on a real
backlog, and it is the difference between a view that scales and one that scrolls. Two things
earn a word beside the count, because both are constant-size and both change what you would
do next: whether the critical path continues past the window, and whether
the count moved because of a what-if. Press b to list them when you actually want
the names.




  Honest about its own staleness. The header always states when the last real
  glab snapshot was taken and how many events have been replayed on top of it.
  A board that silently shows six-minute-old truth is worse than no board.

How it stays current



  ┌─ once, and on 'r' ─────────────────────────────────────────┐
  │  tick.sh snapshot   ──►  full board       ~N glab calls     │
  │  tick.sh graph          (edges + levels)   1-4 seconds      │
  └────────────────────────────────────────────────────────────┘
                     │  cached in $LOOM_HOME/scratch/shape.json
                     ▼
  ┌─ continuously ─────────────────────────────────────────────┐
  │  tail -F  $LOOM_HOME/events.jsonl                          │
  │     ticket_close ........ ticket done, drop it, re-layer   │
  │     gate_verdict ........ PASS moves it to the merge row,  │
  │                           FAIL sends it back to impl       │
  │     mr_merged ........... about to close                   │
  │     ticket_transition ... state label changed              │
  │     lane_spawn/lane_exit  a worker row filled or emptied   │
  │     snapshot ............ carries iid→state + deps whole   │
  └────────────────────────────────────────────────────────────┘
                     │  no network, pure file read
                     ▼
  ┌─ every 2s ─────────────────────────────────────────────────┐
  │  tick.sh lane-status    live pids, turns, staleness         │
  │  re-run shape.jq, repaint                                   │
  └────────────────────────────────────────────────────────────┘



Two data paths, on purpose. The expensive one (glab, whole-board truth) runs
rarely. The cheap ones — a JSONL tail and a directory of pid files — run constantly and carry
every signal the board needs, including the gate verdicts and merges that drive the aux band.
The snapshot event alone carries the full iid→state map and
the deps edge map, so the board survives an entire build with the network down.
It just says so:



 ── loom shape · build-3 · seat-reservations ──────────────────────── 14:41:12 ──
    ⚠ snapshot 45m old — glab refresh failed 3× (network). Replaying events only.
    last event 41s ago · 62 events applied · r=retry
    Not shown reliably: tickets filed in the last 45m, hand-edited labels, new edges.



Read-only, always. This app never writes a label, never takes a lock, never emits an
event. Same class of thing as render-events: a display-only reader. Nothing about
scheduling may depend on it.

Arrow keys are the primary binding



They should have been in the on-screen footer from the start, and now are — the earlier
mocks showed only hjkl, which read as "vim or nothing". Arrows are what most people
reach for, so they lead; hjkl stays as an alias for people whose hands are already
there. Nobody has to learn a mapping.



The one honest cost: an arrow key is not one byte. The terminal sends
ESC [ A, so the read loop has to notice an escape, grab
two more bytes with a very short timeout, and treat a lone ESC as "cancel". That is
about eight lines of bash rather than one, and it is the same eight lines every terminal app
writes. It does not change the language recommendation.



What-if is a modifier, not a screen



Pressing 2 re-runs the round simulation as if max_lanes were 2 and
redraws the same grid. Nothing is written — .loom.yml is not touched, no label
moves, no event is emitted. It goes both directions: press 6 to ask whether more
lanes would help.



It exists because that question is otherwise expensive to answer. Today you find out whether
your pool size is right by editing config, restarting, and waiting a round or two to see. This
answers it in a keystroke, against the real graph. And the answer is often "no": in this build
the graph is four tickets wide at its widest, so a fifth and sixth lane would sit idle every
round — worth knowing before paying for two more worktrees.



Mouse: no, and here is the trade



Straight answer: no mouse in the bash build. Not because it is impossible — it is
roughly 40 lines. The terminal has to be put into SGR mouse mode
(\033[?1006h), the reader has to parse \033[<b;x;yM byte
sequences, and the mode must be switched off on every exit path including a crash, or
the user's terminal is left broken after the app dies.



The bigger cost is not the code. Turning on mouse reporting takes text selection away
from the terminal — click-drag stops selecting and starts talking to the app, so copying a
ticket number out of the board needs a modifier key most people do not know about. On a board
whose whole job is to be read and quoted into a chat, that is a bad trade for the ability to
click a cell you can already reach with one arrow key.




  This is the second thing that could flip the language. Python's curses
  gives mouse handling, and correct teardown, for free. If clicking cells and scrolling matter
  to you, say so — that plus the routed-DAG shape are the two real arguments for Python, and
  either one on its own is enough to reopen the decision.




Language: bash + jq vs Python




  

    
bash + jq recommended

    
    
      
  • Zero new dependencies. python3 appears nowhere in this repo — not one invocation.
    • 
      
  • The hard part is already done. graph.jq computes the depth fixpoint over blocked_by today. The round simulation is one more jq file beside it.
    • 
      
  • bash 3.2 never touches the data. No associative arrays needed, because jq holds every map. bash only paints and reads keys.
    • 
      
  • One test harness. tick-test.sh already stubs glab, launchd and herdr. A bash script drops straight in.
    • 
      
  • House style is already line-oriented — printf, jq -r, four ANSI colour codes, ✓ ✗ ⚠.
    • 
      
  • Full-screen repaint means writing cursor control by hand — about 15 lines of ANSI, plus 8 more to decode arrow keys.
    • 
      
  • No mouse. Doable in ~40 lines, but it costs the terminal's own text selection — see the trade above.
    • 
    

  

  

    
Python 3 + curses not recommended

    
    
      
  • Better redraw, and mouse for free. curses gives diff-based painting, scroll regions, arrow-key decoding and mouse handling with correct teardown — none of which you write yourself.
    • 
      
  • Better at graphs — if the graph work were not already written in jq. It is.
    • 
      
  • Splits the toolchain. One Python file in an all-bash skill, with its own test story, its own lint story, its own review burden.
    • 
      
  • System Python is 3.9.6, stdlib only. No rich, no textual installed. Requiring them adds an install step to a skill that today needs only jq and glab.
    • 
      
  • Still shells out anyway for tick.sh snapshot and lane-status — so it inherits the subprocess plumbing without escaping it.
    • 
    

  





The one case that flips this is the routed DAG drawn above. Real edge routing needs
a layout engine and jq is the wrong tool for it. Nothing else in this proposal comes close —
the grid is a fixed table of cells, which is jq's home ground.

Tests worth writing


    
  
  • A blocker that closes moves its dependents up exactly one round — and a blocker that only reaches merge-queue moves nothing.
    • 
  
  • A ticket in gate does not occupy an impl row, and the freed impl row takes the next ready ticket in the same round.
    • 
  
  • Two tickets ready to merge in one round render as a two-deep merge row, never as two parallel merges.
    • 
  
  • A gate FAIL verdict returns the ticket to an impl row at round n+1, not to the merge row.
    • 
  
  • A ticket over the pool cap spills marked ▪, never ⧗; a worker with no legal work shows ○, never ▪.
    • 
  
  • A dependency cycle is reported, not looped on — graph.jq already sets cycle_suspected.
    • 
  
  • A closed: null blocker (cross-project link, state unknown) counts as not closed, matching graph.jq.
    • 
  
  • With glab unavailable, the board renders from the last snapshot event and says the snapshot is stale.
    • 
  
  • The app writes nothing: no labels, no locks, no events.
    • 




Open questions




  1. Is the rounds-as-rows view worth building at all? It is a second renderer, a
  second set of tests, and a key to remember. Dropping it makes the app meaningfully smaller.
  Keeping it means long titles and heavy blocker lists always have somewhere to go.





  2. Its own script, or a tick.sh verb? The proposal is
  scripts/shape.sh, standalone, because tick.sh is already 172 KB and
  this is display-only. But every other reader — render-events,
  render-log, lane-status — lives inside tick.sh.
  Consistency argues the other way.





  3. Should the herdr viewer get a pane for it? watch-panes.sh already runs
  a ticker strip pane. A shape pane would be a natural sibling — but it is separate work from
  the app itself.
