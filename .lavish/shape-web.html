loom · proposal · ux screens

The shape board,
in a browser

shape.sh answers one question no other loom view answers: is my machine going to idle, and why. It answers it for one repo, in one terminal. This proposes the same answer as a web dashboard that can hold all 28 loom projects on this machine at once — and keeps the read-only discipline that makes the TUI safe.

02 · the screens

Five screens, one page

The dashboard is a single route with a persistent project rail. Nothing below navigates away from the board — the drawer, the beyond panel and the what-if control all resolve in place, because the board is the thing you are watching.

S1 · The board, with the project rail

The rail is the answer to "switch between projects." It lists every directory under ~/.loom — 28 on this machine right now — grouped so the ones with running lanes sit at the top. Each row carries the build label and a live/quiet mark, so the rail doubles as a machine-wide status wall you never have to open.

S2 · Ticket drawer — track and edges, side by side

In the TUI, t and e are full-screen overlays that hide the board. A browser has the room to keep both: click a cell, the drawer opens beside the grid, and the grid stays live behind it. The two overlays become two tabs on one surface.

S3 · Beyond the window, and the blocked inbox

Two lists the TUI compresses to one line each. On the web they sit under the board permanently, because both are things you act on and neither is big.

A blocker outside this build never closes inside it, so its dependent never floats to round 1 — it surfaces here instead. The simulation already runs four rounds past the window so it can name the round, not just say "later."

Out of the machine's hands

Blocked tickets take no part in the round simulation — counting them as future work would make every column after the first a lie. The board excludes them; this panel is the only place they appear, which is why it is always on screen.

S4 · The machine wall

One extra screen the TUI cannot have: every project's board condensed to a single row, so "which of my 28 builds is idling right now" is one glance rather than 28 terminals. This is the screen that justifies the project switcher — see the open question in §5.

03 · how it is fed

Three data paths, unchanged

The dashboard reuses shape.jq's simulation rather than reimplementing it. A thin reader process shells the same commands shape.sh shells, and pushes the result over Server-Sent Events so the browser holds no polling logic.

  L -- "overlaid at render, never cached" --> J
  J -- "SSE: one JSON board per project" --> B

Why the daemon renders JSON, not text. shape.jq today emits a drawn board and a --mode cells JSON map that the cursor navigates by. The web version needs the cell map for every cell, not just positions — so this adds one mode, --mode json, emitting the same simulation as structured data. The drawing code stays untouched, the TUI keeps working, and the two views cannot drift because they run the same reduce.

Read-only, by construction. shape.sh's header states it: writes no label, takes no lock, emits no event, spawns no lane — delete the file and nothing about a build changes. The daemon inherits that rule exactly. It runs snapshot and lane-status and it reads events.jsonl. It does not tick, pause, retry or merge. That is what makes it safe to leave open in a tab for a week.

04 · what will bite

Risks, honestly

risk · blocking

Nothing maps a project back to its repo

The state directory is ~/.loom/<basename>-<cksum of the repo path> (tick.sh:52). A checksum is one-way — from crucible-2014258785 you cannot recover /Users/…/crucible, and the dashboard needs that path to run tick.sh at all.

Fix: write the repo root into $LOOM_HOME/.repo at bootstrap, and backfill the 28 existing homes by scanning for git repos whose path checksums to a known key. Small, but it must land first.

risk · high

28 projects × one snapshot each

A snapshot costs one tracker call per member plus a batched fan-out. The TUI protects the rate limit by never putting it on a timer. A wall over 28 projects that refreshed them all would spend the build's rate limit drawing pictures of the build.

Fix: the wall refreshes only projects with a running lane (4 of 28 here), reuses each project's cached scratch/shape.json for the rest, and labels stale rows stale rather than hiding them.

risk · medium

A board that lies quietly is worse than none

The TUI prints snapshot age and applied-event count in its header for exactly this reason. A browser tab left open overnight is a much better liar than a terminal.

Fix: carry age and event count into every screen including the wall, and grey the whole board past a threshold instead of showing confident-looking stale cells.

risk · medium

A local HTTP server on a dev box

The daemon can shell tick.sh for any project on the machine. That is a lot of reach for something listening on a port.

Fix: bind 127.0.0.1 only, no auth but no external interface, and the project list is fixed to what exists under ~/.loom — the project id is never interpolated into a shell command as a path.

Scope note. Everything above is read-only. Buttons that would change a build — pause the loop, retry a gate, unblock a ticket — are deliberately absent from these screens. They are a real product question, not an oversight, and the third question below asks it directly.

05 · your call

Three decisions before code

Pick one per question and queue it. Anything else, annotate the screen directly.

1 · How much of the machine does it show?

This decides whether the wall (S4) is built at all, and how hard the snapshot-cost problem bites.

2 · What renders the board?

The simulation is 456 lines of jq that the tests already pin. The question is whether the web version runs it or reimplements it.

3 · Can it change a build?

shape.sh is deletable by design. A dashboard with buttons is a different kind of thing, with a different blast radius.
